# Ingestion 2.0.0 behavior

POST /v1/ingestion/batches, internal Authorization Bearer token. GET /v1/ingestion/capabilities requires the same authentication. One batch belongs to exactly one project and environment. Environment is exactly {id: UUID} OR {name: string}. Names support Unicode (including 开发环境), 1..64 Unicode scalar characters, no control characters or surrounding whitespace, case-sensitive. No implicit normalization or default. The UI must ask for environment; do not derive it from domain. The capture scope is domain + path; the plugin binds that scope to a selected project/environment. There is no additional service partition. Selecting a project loads that project’s environments; changing projects discards the previous environment selection. The producer sends the selected project and environment, not a service key.

Producer generates UUID v4 record_id at the first immutable terminal observation, instance_id once per installation/producer, batch_id when assembling a batch. Retry identical records with identical IDs and payload/time/source/scope. Retry a whole batch with its original ID; regrouping may change batch ID. Batch ID is correlation, not dedup identity. Record IDs are namespaced by authenticated user + source.instance_id, NOT token (rotation must not duplicate work). Changing source type/project/environment-ID/record content for an existing record ID returns IDEMPOTENCY_CONFLICT. No API definition version is supplied by producers. Payload_version is only the wire format.

Use batch.schema.json for producer validation. The receiver first validates envelope.schema.json, then each record against batch.schema.json/$defs/Record. Unsupported kinds/versions and malformed records are individually rejected without blocking valid siblings. Invalid envelope/auth/project scope rejects the whole batch. Input unknown fields are rejected in v2. `bytes` describes captured bytes, not JS string length or necessarily complete source length. Body strings and header entries are retained as sent, including business credentials; NO redaction. Backend logs must not print payloads or authorization. Fixtures use synthetic values.

Defaults/advertised maxima: 50 records, 8 MiB entire encoded batch, 4 MiB encoded record, 16 concurrent batches per process, no Content-Encoding compression in v2. Plugin flushes at 20 records OR 4 MiB batch OR 1 second since the first ready record; indivisible record up to 4 MiB goes alone if needed. JSON UTF-8 bytes, not character count, determine limits. Do not truncate data to fit. Persistent queue is independent of the UI's test-only 20-row display buffer. Never evict unacknowledged records. On capacity exhaustion pause capture, keep pending data, explain the condition. HTTP response completion/failure/timeout must be settled before enqueue; no same-ID late body mutation.

Dedup target: project + stable environment ID + method + recognized path template (query not identity). path-template-1 recognizes whole-segment UUIDs, 32/64 hexadecimal strings and unsigned ASCII integers from the first observation. v1/search/latest/date strings and other segments remain literal; preserve case, slash count and trailing slash. Per-project policy may disable recognition, retain numeric segments or exclude segment-boundary path prefixes. Truncated URLs retain literal paths. The authorized batch pins a path identity before head locks; original record/content hash stays untouched. Policy reads occur once per batch, not once per record. Existing historical heads/documents/receipts remain unchanged; the first new normalized observation establishes a template head. Legacy queued observations retain literal processing. The host/domain is provenance, NOT environment identity. Query names and value type, request/response media type, status, and body structural shape determine structural digest. Plain query values are strings. JSON object keys are sorted; numbers are one number type; scalar values are ignored; array length/order ignored but EVERY element's distinct shape is inspected. Empty arrays establish array type but no element type. Comparison is directional: a known populated element schema covers an incoming empty array, but an empty array does not cover newly observed elements. Ignore only when all other fields and metadata are also covered; never replace a richer current head with an ignored empty sample. Array objects with the same field names share a field-level shape for null/unknown and nested-array observations; differing field sets and concrete scalar type conflicts retain alternatives. Coverage concerns fields, not business-value combinations. An unseen null-only field remains inconclusive; a null alternative already present in the baseline does not create a new object variant. Old projections are normalized for comparison, with extraction gaps retained. The comparison algorithm is http-structure-4; existing current heads upgrade lazily from their own stored observation, without scanning history or changing immutable retry receipts. Header names (case-insensitive, preserving presence but not order) participate in structure. Header values are not part of structural identity except Content-Type; dynamic token/cookie/date values do not force changes. Custom header/body business-value semantics are outside v1 structural dedup, not silently inferred. request.body state none is known empty; unreadable/truncated/timeout, URL truncation, response failure or unreadable/truncated headers are inconclusive. Non-JSON body equivalence uses exact encoded content rather than pretending all text/image bodies are equivalent. Oversized/deep JSON is not guessed equivalent.

A complete known current observation can return ignored/DUPLICATE_CURRENT_STRUCTURE. The first observation or changed/inconclusive observation is atomically written without redaction to the downstream inbox, with its idempotency receipt, then accepted/FORWARDED. This is the downstream entry boundary, NOT completed knowledge processing. This stage does not create interface documents, classify, adjudicate or rebuild. pending inbox rows remain for the future processor; they are not discarded or marked processed.

Latest admitted observation baseline is distinct from a future adjudicated API version. It is keyed by project/environment-ID/interface identity; after A→B, another A is forwarded, even if a historical inbox row has A. An inconclusive admission clears the known baseline rather than hiding later complete samples. Future adjudication must explicitly update/invalidate this current comparison projection with a generation; historical API definitions must never be used as an all-time dedup set.

HTTP 200 returns receipt.schema.json with resolved environment:{id,name} (null when every record is rejected before resolution), one result per input item with record_index and echoed record_id (null if invalid). accepted: ingestion_id identifies a durable pending inbox entry. ignored: points to the existing current entry, no new raw payload. rejected: reason_code and retryable. Retry of an existing ID returns its original status/ingestion_id with replayed=true, not a newly computed decision. Current implementations persist compact receipts even for structural duplicates so same-ID altered-content conflicts remain detectable. No eviction/TTL for receipts in v2; budget/storage monitoring and retention policy required before long-term rollout.

Reject reasons: INVALID_RECORD, INVALID_BODY_STATE, INVALID_BODY_ENCODING, UNSUPPORTED_KIND, UNSUPPORTED_PAYLOAD_VERSION, RECORD_TOO_LARGE, IDEMPOTENCY_CONFLICT. Those are not retryable. Storage failure returns HTTP 503/INGESTION_UNAVAILABLE with no batch partial commit; resend unchanged. Overload 429/INGESTION_BUSY with Retry-After, payload/envelope too large 413, wrong Content-Encoding 415, invalid JSON/envelope 400, invalid token 401, project denied 403, unknown project 404, missing local access 503. Respect 401 by pausing authentication; do not clear token on 403 or transient 503. Drop only accepted/ignored from pending upload; permanent rejections require visible failed state. No logging or fixtures with real payload secrets.

Contract changes: update authoritative schemas/behavior/fixtures, regenerate types and manifest, run backend runtime validation + fixtures and plugin converter/receipt tests, then publish a pinned bundle. Plugin must copy/pin exact bundle hashes, not follow latest at runtime. Backend first supports new contract before plugin uses it. Existing manifest is not permission to change meaning without version bump. v1 is retained in legacy/v1 for immutable queued records. New uploads use v2.

## Environment management (same internal Bearer)

GET /v1/projects/{project_id}/environments?page=1&limit=20 returns environment-page.schema.json. POST the same path with environment-write.schema.json returns environment.schema.json (HTTP 200, same-name existing environment reused). PATCH /v1/projects/{project_id}/environments/{id} with {name} renames that environment (HTTP 200). All operations require current local project access. No environment deletion is exposed. Invalid name 400, denied project 403, unknown/cross-project ID 404, conflicting reserved name 409.

Upload resolves environment name in that project and creates if absent, using a stable UUID. Several domains with identical project/environment can dedup across origins. Environment name change retains the ID and current observation head. Old names are retained as aliases: an old queued name-based batch resolves the same environment after rename, and retry idempotency uses resolved environment ID. Aliases cannot be reused for another environment. Same name in another project is independent. Plugin should use selected environment IDs, and use returned environment ID for future newly queued records after a name-based upload; it must not rewrite in-flight immutable records.

v2 removes service_key. Server supports v1 and v2: v1 validates its original field and preserves its original idempotency hash so old queued records can replay, but the field never partitions dedup. Receipt schema_version echoes the input. A v2 payload containing service_key is invalid. Do not rewrite old queued records; future records use v2. Legacy inbox provenance is retained; existing heads are consolidated by latest admitted observation within project/environment/interface. No user data is reset.
