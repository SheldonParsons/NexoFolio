# 持久化整理任务队列（性能计划第一步）

2026-10-12。只实施任务接收、排队、领取、租约恢复和必要合同适配；不改变模型重试策略、并发额度、人工应用流程或 MCP 的 11 个只读方法。

## 接收与范围

- 原开始、单接口整理、organize、resume 路由保留。成功返回 202，进度新增 `task_id`、`task_state`、`queued_tasks`；排队时保留兼容的 `status=running`，以 `task_state=queued` 区分等待和执行。
- PostgreSQL 先提交任务再返回接受，不提前创建候选或准备资料。存储未确认时返回 503 / `CURATION_NOT_SUBMITTED` 及“尚未提交”，不返回 202；响应丢失后可重试同一范围。
- 范围为项目内的全项目或一个规范接口 UUID；接收单接口时通过现有 identity 端口解析别名并核验项目。数据库部分唯一索引和项目锁共同确保同项目同范围只有一个 queued/running 任务。
- 同范围的首个未完成请求决定发起者、parent/resume 意图；后续提交复用它。不同范围独立入队；失败、停止或完成之后再次开始会产生新任务。显式续跑既有候选复用其原任务与候选 ID，重新分配执行代次。
- `GET /v1/projects/{project}/curate/tasks/{task}` 查询任务；`POST .../tasks/{task}/stop` 幂等停止。原进度接口支持 `?task_id=...` 跟踪指定任务，避免被其他范围替换。查询和停止均复用项目权限。

## 调度与一致性

- knowledge 持有状态和事务，adapter 仅实现持久化。runtime 的同一个循环负责领取 queued 和过期 running，使用既有候选执行器、冻结输入、批次保存及 supervise；生产不再扫描候选来启动第二套恢复器。
- 领取在短调度锁和项目锁内完成。每项目最多一个 running；项目按上次领取时间轮换（从未领取者优先），项目内按接收顺序。租约 120 秒、心跳 20 秒保持原值，队列每秒检查一次。
- 运行任务数量以上线配置中既有 `NEXOFOLIO_MODEL_MAX_CONCURRENCY` 为上界；模型适配器内部许可、背压、冷却和字段/描述并发保持原实现。多 API 副本应使用一致配置；本步没有新增跨副本的模型额度控制器或生产调参结论。
- 每次领取增加 generation 并生成 run_id。所有候选写入（开/追加/关批次、冻结资料/取值、心跳、检查点）在项目锁内核验任务有效租约及 owner；旧代次不能写结果或续租。
- 候选创建与任务关联同事务；最终候选状态与任务结束同事务。领取后才读取最新资料，已冻结候选恢复时保持原资料和已保存批次。尚未冻结且没有批次的准备阶段可继续同一候选；不兼容资料、基线变化或手动续跑缺少冻结输入会保留成果并结束此次执行。
- 停止 queued/running 后不会自动领取；已保存批次保留。原 candidate cancel 同时停止排队中的续跑，应用/废弃同事务关闭关联任务（包括显式 parent 请求）。清空沿用“有活动整理则拒绝”，计入 queued，停止后清空原子移除任务与原有内容层。
- 执行和心跳通过已启用账户及当前项目权限重新核验。只持久化发起者身份，不保存登录密码、会话令牌；会话过期不取消任务，账户禁用或撤权不绕过授权。

## 升级

执行现有 `nexofolio-admin migrate`，包含 `202610120001_curation_tasks.sql`。依赖现有系统要求的 PostgreSQL 15+。应先停止旧 API 进程并备份，再迁移及启动新 API；不支持旧执行器和新执行器混跑或只退镜像而不处理数据库。

迁移接纳现存 running 候选，保留候选 ID、冻结输入、批次和操作来源；同项目异常重复的旧 running 保留为 interrupted。历史 partial/interrupted/ready/applied/discarded 保持原状，显式续跑时补任务身份。无法确定发起者的旧任务不能自动绕过权限，需要有权用户手动续跑。新 API 启动后等待原租约过期再接管。

## 验证与复跑

运行 `scripts/test-curation-queue.sh`（可用 `PG_BIN` 指定 PostgreSQL 15+ 二进制目录）。脚本创建并清理独立集群、数据库及合成数据；进程测试只启动本地固定模型/身份上游并清理子进程，不使用用户服务或付费模型。

验收覆盖并发 24 次提交、别名归一、忙时排队、同项目串行和跨项目轮换、双领取者、过期 owner 全写路径、读取最新输入、准备期恢复、停止/应用/废弃/清空、旧安装升级、HTTP 查询/停止权限及落库失败。

真实进程重启验证保留任务/候选及成功批次，只补未保存字段；同时验证会话过期、撤权和账户禁用。测试将已杀死的合成任务租约回拨以触发接管，另以事务测试核验过期条件；这是故障回归，不是生产容量校准或 8 小时隔夜测试。

`cargo test --workspace`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo fmt --all -- --check`，以及前端 `pnpm test`、`pnpm build` 为常规检查。前端排队时可查看和停止，没有新增管理面板。

持久重试/等待关注、管理状态面板、快照分块、MCP/Fetcher 优化、存储清理、容量校准和部署仍属后续步骤，本次未实施。外部模型调用不具备恰好一次计费保证；本步保证已保存结果与执行权的一致性。

## 独立审查后的第一步修复

初次交付的32项隔离测试和346项前端测试未覆盖父子候选关闭、异步执行审计、忙时页面入口和空候选任务身份，不能用这些通过结果证明上述边界。失败复现及修后证据见 [修复报告](../audits/2026-10-12-curation-queue-fixes/report.md)。

- 父候选 apply/discard/cancel 在原项目事务内同时停止关联任务并中断已创建的运行子候选，保留批次、视图和冻结资料；下一任务无需等待旧租约便可准备，旧执行者仍被写入栅栏拒绝。
- 执行复用原有 Audit sink，以任务中持久的发起者身份重建 `WORKER` 上下文。可选 `execution` 字段仅包含 task_id、run_id、generation；接收/停止 HTTP 事件保留实际操作者，执行事件关联发起者，接管另记 `curation.recovered`。不复制登录凭证、原始正文或伪造请求来源；旧审计 JSON 仍可读取。
- 审计仍是原有有界、尽力写入机制，硬退出或存储/队列异常可能丢事件；本步恢复关联和事件发出，不提供恰好一次投递。后台审计说明没有进入公开更新日志。
- `GET /v1/projects/{project}/curate/tasks` 仅返回有权项目的活动任务，供现有进度面板按需切换。提交动作与后台观察分开，其他范围可排队；同范围复用。切换/停止以 task_id 和执行身份判别，不以两个空 candidate/run 值判成同任务。
- 排队及停止状态不展示虚假的执行统计；停止是正常结果。关闭面板重选任务、网络不确定、晚到读取/停止结果、旧候选检查点的任务状态覆盖均有回归。原全屏进度面板可收起以访问页面入口；未增加全局任务管理面板。
- 正式新增用例已纳入 `scripts/test-curation-queue.sh`。浏览器夹具为单独 ignored 测试 `curation_queue_browser`，需要显式私有目录和隔离数据库，不随普通测试启动；不引用审查目录的临时 Cargo 工程。
