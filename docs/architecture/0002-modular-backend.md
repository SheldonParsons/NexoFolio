# NexoFolio 模块化后端架构

日期：2026-09-14

状态：业务设计与演进方案。工程骨架及禅道登录、内部 Token、登录后项目同步和读取准入已实现；采集、目录算法、独立同步和裁决仍为后续工作。实际协议见登录与项目 API 文档。

关联：[技术选型](../decisions/0001-experiment-stack.md)、[实施计划](../plans/0001-backend-foundation.md)
MCP 凭证和工具签名以[MCP 专用 Token 与工具契约](../contracts/0001-mcp-access-and-tools.md)为准。

## 1. 本轮确定的架构方向

- Rust 后端使用 Tokio + Axum + Tower，HTTP MCP 使用官方 rmcp，持久化使用 PostgreSQL + SQLx。
- 一个 Cargo workspace 管理多个业务 library package；API、worker、CLI 统一装配，初期仍按一个系统部署。
- 用户普通登录由禅道验证，本平台保存基础用户映射并签发自己的会话；超级密码走独立的本地验证分支。
- MCP 使用由平台管理入口单独签发的 Token，绑定项目与读写范围；不使用网页登录会话、禅道密码或超级密码访问 MCP。
- 项目只能从禅道同步，管理 API、CLI、MCP 都不提供任意创建项目的功能。
- 浏览器流量接收是独立 HTTP 批量入口；agent 查询与受控变更通过 HTTP MCP 提供。
- 高频接收、正式知识处理、触发判断、重构方案生成分别负责不同工作；触发器和重构器独立编译。
- 先把依赖方向、数据归属、事件和返回契约做好，再逐步实现策略。
- 后续支持接口文档跨项目移动/复制，以及选中部分接口导出；当前先落实稳定身份、归属与正文分离、显式引用和可版本化导出模型。

待确认：禅道版本/版本类型、同步账号、具体权限接口、采集负载与报文大小。
已确定：超级密码不请求禅道验证，允许登录任意已有用户，不创建用户、不增加其项目权限；项目权限跟随禅道。本轮只定义接口，等待用户提供接入资料。

## 2. Rust Web 和模块化概念

| 名称 | 在本项目中的作用 |
| --- | --- |
| Axum | 路由和请求处理，类似其他语言的 Web 框架 |
| Tokio | 调度异步网络和数据库工作，不是持久任务队列 |
| Tower | 身份上下文、限流、超时、追踪等中间件的组合基础 |
| rmcp | MCP 协议和 Streamable HTTP 传输 |
| SQLx | 数据库查询、连接池、事务和 SQL 迁移 |
| module | 一个 crate 内部的代码分区和可见性边界 |
| crate/package | 可独立编译、测试并声明依赖的组件；本方案业务包各含一个 library crate |
| workspace | 在一个仓库里管理这些包、锁文件和构建命令 |
| trait | 某种能力的调用契约，让实现可以替换 |

Rust 可见性和依赖声明能够加强边界；仍需 CI 检查依赖白名单，避免后来随意增加依赖或扩大公共接口。
不引入运行时动态插件。策略作为编译期实现注册，参数和启用规则使用带版本的配置管理。

每个业务包只通过 lib.rs 导出必要的请求、结果、服务和 ports。内部数据库行、缓存键和辅助函数保持私有。
contracts 只存真正跨边界的稳定类型，不成为收纳所有模型或工具函数的目录。

### 依赖方向

| 包 | 允许的本地依赖 | 禁止事项 |
| --- | --- | --- |
| contracts | 无 | 不包含数据库、HTTP、模型 SDK |
| access / knowledge / intake / triggers / rebuild | contracts | 相互不直接依赖；不依赖 Axum、rmcp、SQLx、模型 SDK或队列实现 |
| application | contracts 和上述业务包 | 不依赖 infrastructure；通过 ports 调用外部能力 |
| infrastructure | contracts、业务包/application 的 ports | 不决定登录权限、正式定义或目录发布策略 |
| apps/backend | application、infrastructure、必要 DTO、传输库 | 不在路由函数里实现去重、裁决或重构规则 |

业务编排发生在 application。基础设施实现 ports，最后由 wiring 注入。
不同模块共享一个 PostgreSQL 并不表示可以任意互写：SQL 按表的所有者归档，跨模块事务使用明确的应用操作和事务 port。
归类和重构产生建议或候选；正式记录更新与目录发布只通过 knowledge 定义的规则和 application 的事务操作。

## 4. 禅道登录、基础用户与项目同步

### 普通登录

```text
HTTP 登录 → access 登录规则 → 禅道认证 port
         → infrastructure/zentao 请求目标实例
         → 验证身份 → 更新本地用户映射 → 复用有效内部 Token 或签发新的内部 Token
```

本地保存 user_id、禅道实例、外部用户 ID/账号、显示名、必要联系方式、状态和最近登录时间。
外部身份由禅道返回并核实，不信任客户端声称的用户 ID。普通密码不持久化，不进入日志。
外部 API 若只返回 Token，再通过该版本支持的身份接口取得用户信息；不能把获取 Token 与完整身份映射混为一谈。
普通登录验证失败或禅道不可达时，不自动切换为超级密码成功。

本平台会话独立于禅道 Token。插件使用采集授权；MCP 使用平台管理入口签发的专用 Token，并验证绑定项目、有效期、撤销状态与当前授权，不逐请求回禅道登录。
内部登录 Token 生命周期按用户最新规则：每次普通登录先通过禅道认证，再按稳定本地用户身份查询 Token。没有 Token 或已过期时创建新的、有效期为 3 个月的 Token；已有未过期且有效的 Token 原样返回，Token 值、签发时间、到期时间均不改变，不使用滑动续期。
并发登录通过事务/唯一活动凭证约束收敛到同一有效 Token，不能每次登录生成一份。无效或被本地撤销的凭证不复用。
后续业务请求只验证本平台 Token 和本地项目授权，不调用禅道，不因禅道 Token 失效而自动使内部 Token 失效。权限以最近成功同步的本地记录为准，不另加一个会触发远程校验的权限快照 TTL。
若要在后续登录时返回同一个不透明 Token，存储需保留可恢复的受保护 Token 值（例如密钥配置独立保存的加密字段）和用于查验的摘要；仅保存不可逆摘要无法原样返回旧 Token。这是内部登录凭证的存储需求，不改变专用 MCP Token 的仅签发时显示规则。
本次 3 个月和复用规则针对内部登录 Token；MCP 专用 Token 仍独立签发和管理，不随网页登录刷新。
access/mcp_tokens 负责签发和撤销规则，HTTP 管理入口使用平台会话；MCP Token 本身不能管理 Token。详细签发接口和七个工具见独立契约文档。
项目同步如需长期凭据，单独配置同步身份与权限，不能依靠长期保存每个人的普通密码。

### 超级密码

独立 EmergencyAuthenticator 分支，本地验证后使用相同的内部 Token 复用/创建流程。本次登录方式记录在登录审计中，不通过修改已有 Token 来记录 auth_method。
用户已选择“任意已有用户”：根据输入账号查找已有本地用户，以该用户身份登录，不创建身份、不改变其原项目权限。现已通过 ConfiguredEmergencyPassword 与 PlatformAccess 实现；未设置 Argon2id 哈希时禁用此分支。
密码配置存放于部署密钥配置，服务端使用密码哈希进行验证。每次输入超级密码均不调用禅道。
超级密码认证不等于允许本地创建项目；它仍受项目仅能同步的规则约束。

### 项目同步

projects 以 (zentao_instance_id, external_project_id) 唯一映射到本地 project_id。
当前项目同步方案：NexoFolio 和 Fetcher 普通禅道登录成功后，共用服务端登录后同步流程，按本次用户可见范围增量汇集项目；不以超级同步账号为前置条件。
同步时机已确认：每次普通禅道登录成功后同步一次项目与该用户可见范围，即使复用旧内部 Token 也执行同步。未来增加已登录用户主动调用的独立项目同步接口，无需重新执行本平台登录流程。
两个入口复用同一个同步应用服务。独立同步使用内部 Token 验证调用者，不重新生成或延长内部 Token；普通业务请求与 Token 验证不隐式触发同步。
独立同步仍需要后端持有可用的禅道访问凭据，内部 Token 不能直接作为禅道 Token 使用。登录时取得的禅道 Token 后续如何受保护地保留，以及失效后的恢复方式，待开发独立同步接口时验证；不默认保存普通密码或承诺禅道凭据无限有效。
每次分页读取用户可见的全部状态项目（当前实例实测支持 status=all），本地仅为不存在且 status=doing 的项目建立映射。已有项目不重复创建或重建目录，但根据实际响应更新外部状态与观测时间；不存在且非 doing 的项目跳过。
不能只请求 doing 来维护状态，否则项目关闭后会从结果消失，无法区分状态变化和权限收窄。
项目状态字段与项目权限分开；状态变化不删除项目、接口、修订或证据，也不擅自推导新的只读/停用策略。
项目库是成功登录用户可见项目的逐步并集，不保证一开始覆盖整个禅道。状态新鲜度以最近成功观测为准，不保证实时更新。
超级密码登录没有禅道 Token，不能执行这一轮普通登录同步或伪造权限刷新。
创建用唯一约束处理并发登录；状态更新保存观测时间/同步代次，拒绝更旧的同步结果覆盖已应用的新观测。
项目元数据和本次用户可见范围分开处理，不能把项目库全体记录授予每个用户。部分同步失败不删除项目、不替换完整权限快照；错误状态对调用方可见。
同步字段包含外部名称、状态、父级信息、同步时间和来源版本；本地采集映射等配置与外部字段分开。
仅提供读取与受控同步操作；创建本地映射只能由完整验证过的同步结果触发。
分页拉取必须记录同步运行、覆盖范围和是否完成；部分分页失败、权限收窄或空结果不能直接当作项目被删除。
已归档或确认移除的项目先标记状态，保留知识和历史；是否停止新采集由明确策略控制。
项目内容访问权限跟随禅道，不能仅凭“已登录”推导；当前 ProjectPermissionSource 尚未接入真实权限来源。
当前登录流程使用 LoginProvider 与 PlatformAccess：从完整项目列表和 profile.view.projects 建立本地项目读取关系。原 ProjectPermissionSource 的动作权限仍未实现，不借“可进入”赋予写入或裁决权限。

#### 平台项目列表可发现，项目内容仍需授权

当前用户决定：登录平台后，可以在项目列表看到平台已同步的项目，无访问权限的项目仍显示；进入时由前端提示，后端必须执行真正的访问控制。
建议 GET /v1/projects 在当前部署/组织范围内返回项目基础卡片：project_id、name、status、access_state、can_access、reason_code。不因该用户缺少项目内容权限而从平台列表过滤记录。
access_state 区分 allowed、denied、unknown；只有 allowed 时 can_access=true。unknown 表示本地权限尚未取得，不能误提示为确定的禅道拒绝。已成功同步的本地授权不另设需要访问禅道的过期刷新规则。
该规则只开放项目存在、名称和状态等明确列出的元数据，不返回无权限项目的目录摘要、接口数量、成员、文档内容或采集信息。
项目详情/目录/搜索/接口读取/样例/历史/写入/导出等操作统一进行服务端授权，不信任前端传回的 can_access，也不能只在“进入项目”时检查一次。
已认证且明确无权限时，HTTP 返回 403，业务码 PROJECT_ACCESS_DENIED，可提示“你暂无该项目的访问权限，请联系项目负责人或禅道管理员”。
内部 Token 缺失/过期/无效返回 401；本地授权数据不可用或尚未建立时拒绝访问，返回 503 / PROJECT_ACCESS_UNAVAILABLE。禅道暂时不可用本身不阻止使用已同步授权访问本平台。
列表状态只是生成该列表时的提示，不替代执行时的本地授权检查。同步失败不删除项目、不覆盖已有完整授权；禅道权限变动只在下一次成功同步后反映到本平台，不声称实时撤销。
MCP 和 Fetcher 的凭证范围仍单独约束：平台列表的发现权限不扩大 MCP Token 的项目集合，也不允许插件向无权限项目写入。MCP list_projects 继续只返回有效授权项目。
未来出现多组织部署时，项目发现仅在所属组织内开放；本规则不授权跨组织列项目。

禅道官方分别提供 v1/v2 API，具体路由、认证与分页行为按实际版本选择适配器。业务模块只依赖 ExternalIdentity 和 ExternalProject 等归一化契约。

## 5. 核心数据如何保存

| 内容 | 数据归属 | 建议存储 |
| --- | --- | --- |
| 用户、身份映射、会话 | access | users、external_identities、sessions、grants |
| MCP 专用凭证 | access | mcp_tokens、mcp_token_projects / scopes：秘密摘要、所有者、范围、有效期、撤销状态 |
| 禅道实例与项目映射 | access | integrations、projects、project_sync_runs、project_capture_bindings |
| 接口身份和当前状态 | knowledge | records：稳定 ID、project/service/method/path/version_scope、状态和当前修订 |
| 接口定义与历史 | knowledge | record_revisions：不可变 JSONB 定义、来源、确认状态 |
| 浏览器观测与代表样例 | knowledge | observations / evidence：结构摘要、有限代表样例、来源和时间 |
| 已识别的结构变体 | knowledge | observation_variants：接口 ID、结构指纹、规则版本、处理状态、关联提案 |
| 待处理输入与回执 | application | capture_inbox、receipts：可靠接收、去重键和处理结果 |
| 结构差异与待裁决 | knowledge | change_proposals：基础修订、差异依据、来源、裁决状态 |
| 目录和引用 | knowledge | catalog_versions、nodes、placements、aliases |
| 构建、事件与实验 | application | jobs、events、outbox、build_inputs、evaluation_runs |

records 不以目录路径作为主键。目录是节点与引用关系，正文只有一份；待分类是各目录版本独立计算的视图。
interface_id 在系统内独立于项目、服务和路径；当前项目/服务归属是可变关联。下文的“身份键”用于当前范围的采集匹配和去重，不是不可变主键。
JSONB 用于灵活定义，身份、版本、关联和状态仍使用明确字段与约束。
首次抓到的接口可建立 observed 状态的记录，保留观测依据；单次响应不能生成“已确认必填”等结论。
已知同结构流量通常不保存每次完整响应、不逐条更新 last_seen；如需次数和时间统计则合并批量更新。
代表样例按状态码、结构变体、媒体类型和场景选择并设置容量；授权允许采集不等于需要长期保存全部流量。

## 6. 高频接收链路：intake

入口建议：POST /v1/captures/batch。它是 Chrome 插件的批量 HTTP 入口，和 /mcp 共用应用能力但使用不同传输契约。
单条也可作为一个元素的批次发送。批量上限同时约束条数、解压后字节数、单条大小和解析深度。
用户指定/授权的项目与服务映射由服务端核实；host 只是映射线索，不凭 host 自动创建项目。

```text
本平台会话与采集范围校验（一次/批）
  → 报文边界、类型和结构校验
  → 规范化接口身份
  → 完整报文重复判定（可选快速层）
  → 观测结构指纹 + 已知变体缓存
       ├─ 已识别、已持久处理、无新信息 → ignored
       └─ 未知/不完整/疑似差异 → 批量查库和唯一约束去重
            → 创建 observed 记录，或可靠接收为待分析项
            → 事务提交后返回，后台继续知识处理
```

### 如何判定“相同”

身份键：项目 + 服务/环境映射 + HTTP 方法 + 规范化路径 + API 版本范围 + 必要的业务操作区分项。
网关统一路径但以 action 等字段区分操作时，区分规则必须显式配置。不能把所有数字路径盲目合并。

结构指纹包含：算法版本、身份规则版本、请求参数位置/名称/观测类型、请求体结构、响应状态码、媒体类型、响应结构、配置指定的重要头或操作区分字段。
对普通业务标量值做抽象，不把订单号、时间戳、分页条数、数组长度变化直接当成定义变更。
重要业务值如枚举含义或错误码需要独立的观察策略，不能因为结构相同就声称它们没有变化。

示例：id=1 与 id=2 可是相同观测结构；id 从 number 变为 string 是不同结构；新增字段进入分析。
null、空数组、缺失可选字段和多态返回都是不确定性来源，不直接推断字段删除或类型替换。
结构指纹差异只是“值得分析”的信号。后台结合正式定义、已知变体与多次证据判断是否形成待裁决。

### 性能边界

- 整体成本至少随收到的字节增长；服务端不能不读报文就可靠证明没有变化。
- 插件可以先做本地合并/抽样和批量上传，但插件提供的指纹只作线索，不能作为唯一的服务端验证依据。
- 同结构指纹需要检查相关结构。若只抽样数组前几项、截断正文或超过解析预算，必须标记 incomplete 并进入受限分析，不能返回确定的 ignored。
- 第一版使用可解释的解析与指纹方案；更换解析器、哈希实现和缓存库由 profile 决定。
- 有界缓存存放已持久处理的变体状态，键包含项目、身份/结构规则版本及相关记录代次；不能先写成功缓存再提交数据库。
- 缓存失效、重启或多实例不共享缓存只允许增加数据库读取，不能丢变化。缓存落后于规则、修订或权限版本时必须失效或回源。
- 多实例重复首次采集通过数据库唯一约束、幂等键和条件写入收敛；进程内并发合并仅是优化。
- 在热命中路径上禁止模型、禅道请求、重构器和逐条持久事件；数据判重争取零数据库读写，但必要的会话/授权检查另行计入测量。
- 授权缓存的撤销传播时延与强一致要求明确建模，不能用一个 TTL 同时声称零查询和即时撤销。
- CPU 密集解析需要有界并发，必要时转入受限 blocking 任务；不能占满 Tokio 网络执行线程或开无限任务。

### 接收回执与可靠性

批次返回逐项结果：ignored、created_observed、accepted、rejected，附 record_id 或 ingestion_id 及原因。
created_observed 仅在记录事务提交后返回，此时记录可读且明确标注 observed。
accepted 仅表示输入已可靠保存并待处理，不代表正式定义已经更新；调用方可凭 ingestion_id 查状态。
ignored 只能用于已处理的已知观测；正在处理的重复输入关联已有回执，不新建任务。
异步接收必须先持久保存输入引用、必要内容和 outbox 再确认；不能只写入内存队列就返回 accepted。
队列满、持久化失败或服务超载时返回可重试错误和退避提示，插件按单条幂等键重试未接受项。

## 7. knowledge 与后台处理

application/processing 将待处理观测交给 knowledge：

1. 匹配稳定接口身份，重检当前修订和已知结构变体。
2. 确认仅为已知观测则结束；更新统计按窗口聚合。
3. 新接口建立 observed 记录，形成待归类事件。
4. 新信息保存必要证据；与正式定义冲突时合并或创建待裁决提案。
5. 只有发生知识层面的新增、已确认变化、归类困难或检索问题，才发出供触发器消费的语义事件。

classification 是轻量的现有分类匹配能力，与目录重构不同：通常给新接口找现有位置即可。
重构器不能直接写正式定义；提案未裁决不能触发自动更新正式字段。

## 8. 触发器：triggers

输入是有版本的语义事件、项目/目录指标和策略配置；输出 TriggerDecision，不执行重构。
支持首批事件：RecordDiscovered、RecordRevisionApplied、ClassificationUnresolved、RetrievalProblemObserved、ScheduledInspection、ManualInspection。
高频重复捕获不产生逐条触发事件。待裁决数量可形成独立的观察指标，但不能当作已确认结构变化。

结果形态：NoAction、Inspect(scope, reasons)、RequestRebuild(scope, constraints, priority, policy_version)。
scope 可以是节点、子树、跨节点集合或整个项目；触发器描述问题和约束，具体策略由重构规划器决定。
规则注册表负责启停规则、记录原因和指标；不通过手写散落 if 条件把触发逻辑放进 intake 或 HTTP 路由。
定时检查和人工检查与知识事件通过同一个触发契约接入。
application 将同范围意图合并、冷却、去重并调度，避免多个触发器同时发起互相冲突的构建。

## 9. 重构器：rebuild

输入：明确的 RebuildRequest、固定数据快照、现有目录、人工边界和策略配置。
输出：CandidatePlan、变更说明、受影响记录/节点、输入版本和评估结果。

内部拆成：

- Planner：比较不调整、修补摘要/别名、移动引用、增类、拆分、合并、子树重建和全项目重建。
- Strategies：执行选定的方案。首轮实现小范围重归类与子树重建，其他策略先明确契约，逐步实现。
- Evaluator：检查覆盖、引用、业务边界和查询表现，决定候选是否符合发布条件。

knowledge 的发布规则与 application 的事务发布器负责切换正式版本；rebuild 无数据库权限，不更新指针。
全量与局部重构使用同一候选和评估协议，局部候选必须声明 patch 范围并保留未修改的节点身份。
快照之后的流量通过有序事件补充。新接口在旧目录和候选目录各自归类，无法归类时留在各自待分类视图。
任务执行代次、检查点、条件发布和回滚沿用实施计划中的一致性规则。

## 10. 数据流与禁止依赖

```text
普通登录 → access → 禅道适配器 → 本地用户/会话
项目同步 → access/projects → 禅道适配器 → 本地项目映射

Chrome → HTTP → application/capture → intake
                                  ├→ 已知观测快速结束
                                  └→ 可靠接收/新观测记录 → 后台 processing
                                                     → knowledge
                                                     → 语义事件 → triggers
                                                     → 重构请求 → rebuild
                                                     → knowledge 发布规则

Agent → HTTP MCP 专用 Token 校验 → application → knowledge 的目录/读取/搜索/变更能力
```

禁止 intake 引用 rebuild、triggers、禅道或模型 SDK；禁止 triggers 直接执行 SQL 或调用重构实现。
禁止 rebuild 自动裁决接口定义；禁止 access 调用接口采集或目录算法；禁止 MCP 绕过 application 修改数据库。
infra 可以实现多个模块的 ports，但领域决策不能藏在 SQL 查询、缓存回调或请求中间件中。

## 11. 首阶段验收以模块边界和高频入口为重点

### 模块边界

- 使用 cargo metadata 在 CI 检查本地依赖有向图、禁止边和核心包禁止的传输/数据库依赖。
- 业务包可独立 cargo test；触发和重构可在无 Axum、无禅道、无真实模型的测试中验证契约。
- 新增一种触发规则只改 triggers 实现及注册/配置，不修改 intake。
- 新增一种重构策略只改 rebuild 和配置，不修改登录、项目同步或 MCP 工具契约。
- 禅道版本适配变化只修改 zentao 适配器及相应契约测试；稳定归一化契约变化需显式评审。
- 发布测试证明 intake、triggers、rebuild 不能绕过正式发布和裁决入口。

### 性能与正确性

先确定并记录服务器规格、请求并发、批大小、解压后报文大小、接口基数、重复比例、缓存命中率和新结构比例。
测试热缓存、冷缓存、多实例、同一接口突发、不同接口高基数、混合负载、超大正文和服务重启。
单独记录 HTTP 接收 P50/P95/P99、CPU/内存、数据判重查询/写入次数、解析耗时、队列积压和新信息可见延迟。
不得把 accepted 的低延迟当作后台处理完成时间；分别报告接收和可见时间。

用重复观测占 95%/99% 的实验负载与包含较多新结构的负载对比，比例只是测试变量，不是已知真实流量。
正确性集覆盖：值变化、字段增减、类型变化、空数组、null、多态返回、action 路由、错误码、同结构不同语义值、规则更新和并发裁决。
先构建朴素但可验证的分类/指纹参考实现，对比优化实现的漏判和误判；性能优化不得吞掉变化。
至少验证：相同观测不重复写入、不重复发起裁决、不产生重构风暴；停掉模型/重构 worker 后重复观测仍能快速响应。
数值性能门槛在首次基线压测后确定，不预先承诺毫秒级响应或固定吞吐量。

## 13. 为后续跨项目迁移与选择性导出预留

本节是建模约束，迁移/导出功能后续实施。优先理解为同一实例内把接口从项目 A 移到项目 B；导出包同时为将来跨实例导入预留格式。

### 当前就需要做好的部分

1. interface_id 使用系统级稳定 ID，不能包含项目 ID 或目录路径。项目内去重键可以随归属调整，不能把其哈希当作永久身份。
2. 项目与服务绑定独立保存。请求/响应定义、说明和样例不依赖本机绝对路径或某个数据库行号。
3. 历史修订保持不可变；归属迁移写独立事件和历史，不能重写旧来源。需要反映新绑定的当前快照可生成新修订。
4. 共享 Schema、证据、业务资料采用明确关联，不能只把引用藏在自由文本里。Markdown 中的普通说明链接与可解析的知识引用分别处理。
5. 对外导出使用带 format_version 的业务数据结构，由内部存储映射生成，数据库表结构迁移不直接改变导出格式。
6. 定义、证据、目录、搜索索引分别存储；导出定义不要求复制整个项目或搜索向量。

### 跨项目移动

移动保留接口 ID，更新当前归属；复制产生新的接口 ID，并保留来源映射。两种操作不能混用。
目标必须是已从禅道同步且调用者有权写入的项目，源项目要求迁出权限；不能借迁移创建项目或扩大 Token 范围。
目标服务映射、同方法/路径/版本冲突、目录归属与关联资料范围在迁移计划中明确。
发生身份或定义冲突时形成待裁决计划，源记录保持原状，不自动覆盖目标或合并两个稳定 ID。

单个接口移动的正式提交用一个事务校验归属版本、更新关联、处理当前目录引用、写源/目标项目事件和 outbox。
同时涉及两个项目的锁按固定顺序取得，避免反向迁移产生死锁；批量移动需明确整体原子或逐项回执语义。
目标优先尝试已有分类，无法确定时进入目标目录待分类视图。旧目录即使仍有历史引用，读取时也必须按当前归属和权限过滤。
旧项目 Token 不会因为知道接口 ID 而继续读到新项目内容；可见的重定位信息同样需要权限判断。
证据和业务资料不能因移动一个接口就连带迁移其所有共享关联内容；迁移计划明确哪些内容随行、哪些保留受限来源引用。

迁移也影响采集匹配。旧归属缓存必须失效，事务中再次检查项目/归属版本，避免迁移期间的旧任务写回原项目。
保留旧采集键的重定位标记，阻止迟到的插件流量默默在源项目重建同一记录。
采集映射是否同步调整由迁移选项明确；不能仅凭旧流量的 host 或路径把请求转写到无授权的新项目。

### 选中部分接口导出

输入最终解析为一份固定的 interface_id + revision 清单；可由手动选择、目录选择或搜索结果产生。
先确定选择范围与数据快照，再生成文件，避免一边导出一边把后续新接口也纳入。
默认可导出所选接口的当前定义与说明；是否包含目录、历史和样例作为独立选项。

建议格式：

- 版本化 JSON 数据包：用于较完整地迁移，携带 manifest、稳定来源标识、所选记录和必要关联。
- OpenAPI：用于交换支持的 HTTP 定义；业务裁决、完整历史等信息需扩展或伴随清单，不承诺无损。
- Markdown：用于阅读和分享。

数据包可以生成 ZIP，里面使用相对路径：

```text
manifest.json
interfaces/<export-id>.json
schemas/<schema-id>.json          # 所选定义依赖的共享 Schema
evidence/<evidence-id>.json        # 仅显式选中且有权导出的样例
```

收集必要的 Schema 引用闭包，但不自动扩展为导出所有关联接口。超出授权或无法解析的依赖明确列入清单，并标注结果不完整或阻止对应格式导出。
只导出与所选接口相关的目录祖先和归属，避免带出无关项目结构。
Token、密码、会话、后台任务和缓存不属于接口文档导出内容。
跨实例导入时，以来源实例和原接口 ID 记录溯源，默认映射到新的本地 ID；不能仅凭外部包中的 ID 覆盖本地记录，也不能自动创建禅道项目。

### 模块安排与后续验收

迁移规则归 knowledge，跨项目授权归 access，application 编排迁移计划与事务；infrastructure 实现存储。
导出使用独立的导出数据模型和格式转换器，后续在 application 增加 export 流程，不让每个 HTTP/MCP 路由自行拼装文件。
暂不新增普通 MCP 迁移/导出工具，也不实现文件生成；当前七个工具保持其职责。
后续重点验证：稳定 ID、源/目标权限、冲突不覆盖、并发流量不重建、选择范围准确、引用完整，以及版本化数据包的导出/导入对照。
