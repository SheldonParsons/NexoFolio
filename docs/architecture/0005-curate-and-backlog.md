# 0005 整理（curate）设计与后续工作清单

状态：设计已与用户确认，实施未开始。
上游：[0002 抓取器与模块划分](0002-fetcher-and-modules.md)、[0004 阶段 3 计划](0004-stage-3-plan.md)。

本文回答三件事：整理由哪些阶段组成、每种内容的生成依据是什么、还欠哪些工作。

---

## 1. 为什么需要整理

录入（intake + observe）已经能从真实流量里归纳出接口身份、字段结构、出现规律和真实样本。
但它产出的东西里**没有一个字是人话**：没有接口名称、没有描述、没有目录、没有字段说明。

整理是把这些补上的唯一环节，也是 NexoFolio 区别于普通 Swagger 的唯一理由。
Swagger 只有开发者声明的类型；我们有真实流量里实际出现过的值，以及接口之间的实际调用关系。
后者是 Swagger 结构上给不出来的，整理必须把它变成文档内容，否则这个产品没有存在必要。

## 2. 设计原则：阶段之间解耦

> 用户原话是「各个阶段在代码和设计思想上都尽量耦合」，但给的理由是「后续可能会修改和增加很多东西」。
> 按理由推断，要的是**解耦**（阶段可独立替换、可插入新阶段），本文按解耦设计。如果理解错了请纠正。

约束如下，后续加阶段时不得违反：

1. **每个阶段是一个独立的 pass**，签名统一：吃「项目 + 上一阶段产出」，吐「knowledge 写入命令」。
   阶段之间不互相调用函数，只通过命令流和存储衔接。
2. **阶段不直接写数据库**。所有落库走 knowledge 的写入命令，命令自带作者与来源（人 / LLM / 规则）。
   因此新增阶段不需要碰存储层，也不需要碰回滚逻辑。
3. **阶段自己声明失效条件**，形式是「给定项目状态，返回需要重算的接口集合」。
   调度器只负责求并集、排序、并发，不知道任何阶段的内部逻辑。
4. **是否调用 LLM 是阶段的私事**。规则阶段（关联发现、信封识别）和 LLM 阶段（内容补全、目录整理）
   在调度器眼里完全一样，共用同一个预算与轮次机制。
5. **阶段顺序由数据依赖决定，不由代码顺序决定**。声明依赖，调度器排序。
   目录整理依赖内容补全的产出，这个依赖必须是声明出来的，不能靠调用次序隐式保证。

一句话：加一个新阶段应该只需要写一个 pass 并声明它的依赖和失效条件，不改其它任何东西。

## 3. 我们手上的原料

所有生成内容的上限。没列在这里的东西，今天生成不出来。

| 原料 | 存在哪 | 内容 |
|---|---|---|
| 方法 + 路径模板 | `observe.endpoints` | 真实流量归纳，路径参数已成 `{name}` |
| 字段结构 | `observe.fingerprints.structure` | 位置（path/query/请求体/响应体+状态码）、字段路径、类型、出现标签、环境间是否不同 |
| 真实样本 | `observe.fingerprints.sample` | 每种结构第一次观察的完整请求响应，含 header 与真实值 |
| 调用统计 | `observe.fingerprints` | 按 (接口×环境×地址×结构) 的次数、首次/末次出现 |
| 服务地址 | `observe.service_addresses` | 地址、调用次数、归属裁决 |
| 环境 | `observe.base_paths` | 环境列表与各自 base path |
| 声明（若同步过 Swagger） | `observe.declarations.structure` | `summary`、`description`、`tags`、`operation_id`、`deprecated`、参数描述、必填标记、响应描述、示例 |

已丢弃的原料：采集契约 `Context` 里有 `page_title`、`page_url`、`interaction_id`、`seq`，
插件会上报，`CanonicalObservation.context` 也接住了，但 observe 之后**没有任何一处引用，也没有存储列**。
见 §7.1。

### 3.1 字段变更 vs 字段本来可选

已实现，不用 LLM，在 `modules/observe/core/src/facts.rs`。判定看出现区间与缺失区间在时间上是否重叠：

- 重叠 → 同期有时发有时不发 → `Optional`
- 不重叠、前缺后有 → `Added { since }`；反之 `Removed { since }`
- 多个非空类型在时间上重叠 → `Polymorphic`；一个类型替换另一个 → `Added`
- 同字段在一个环境 `Always`、另一环境 `Absent` → 置 `differs_between_environments`

门槛防止样本少就下结论：不足 5 次调用一律 `Observing`；判 `Added` 需变化后至少 10 次；
判 `Removed` 需 20 次且跨 3 天。达不到就退回 `Observing`。

当前真实项目里大部分字段是 `Observing`，因为调用次数未到门槛。这是正确行为，不要为了页面好看降门槛。

### 3.2 示例是多份，结构也是多份

`fingerprints` 主键是 `(endpoint_id, environment_id, address, hash)`，`hash` 是结构指纹。
同一接口每种不同结构独立一行、各带一份 `sample`。
「有些字段某些场景发、某些场景不发」的两种场景 hash 不同，就是两行两份示例。

缺口：一个结构只留第一个样本，导致枚举取值收集不全（同结构的后续调用值丢失），
且示例代表性随机（可能刚好抓到空列表）。见 §7.2。

## 5. 整理全过程

用户点一次【整理】，按顺序发生五步。前两步不发 LLM 请求。

### 5.1 范围判定（无 LLM）

取项目全部接口，对每个算内容指纹（结构 hash + 路径），与上一轮记录比对，分出需要重算的集合。
失效条件有三类，缺一不可：

1. 自身结构变了
2. 从来没有描述
3. **关联集合变了** —— 见 §5.3，这条是最容易漏的

### 5.2 关联发现（无 LLM，全量）

绝大部分关联可纯靠值匹配算出，不需要模型。在 `fingerprints.sample` 里跑，四类信号：

- **字典引用**：某接口 `dictCode` 参数的值，字面等于另一接口的字段名
  （样本里出现过 `dictCode=consultType`，而某接口有字段 `consultType`）
- **列表到详情**：某接口响应里的 id 值，出现在另一接口的路径参数位置
- **前置依赖**：某接口返回的字段值，等于另一接口请求体某字段的值
  （`/slider/gen` 的 `data.uniqueId` → `/oauth/token` 的 `sliderCaptchaId`）
- **枚举子集**：某字段的取值集合，是某字典接口返回项的子集

产出一张关联图，通过 knowledge 写入命令落库。

顺带效果：**字典 / 枚举接口成为一等概念**。它们在 Swagger 里是最没信息量的接口
（返回 `{label, value}` 数组，看不出用途），在这里却是整个项目的语义字典 ——
一旦识别出来，项目里所有光秃秃的 `status: 3`、`type: 1` 都能被翻译。
这比目录整理更能体现「新一代接口文档」。

### 5.3 内容补全（LLM，按接口并发）

对 §5.1 选出的接口，每个一次 LLM 请求，默认并发 8。

送入：项目名、方法、路径、剥掉信封后的字段树、1~2 份真实样本（凭据字段值换占位）、
该接口的关联、以及同项目已命名好的 3~5 个邻近接口作风格参照。
取回：接口名称、一句话用途、值得说明的字段的描述。

深字段树要裁剪：`getRootOrgTree` 有 130+ 字段但是递归结构，重复层级只送一层并注明「此结构递归嵌套」；
数组只送前两个元素。

**为什么失效条件必须包含关联变化**：B 接口有字段 `productSeries`，在枚举接口录入前，
最好的描述只能是「产品系列」；枚举接口录入后，正确描述是
「产品系列，取值来自 `/toolDictItem/select?dictCode=productSeries`」。
B 自身一个字节没变，但描述已过期。
所以失效条件不是「我变了」而是「我或我周围变了」。
这种变化只单向增加 —— 项目里接口越多，每个接口能说的话越多。

规模性质由此保住：新增一个字典接口，受影响的是引用它的十几个接口，不是全部 500 个。
做法是关联图与上一轮做差，边变了的接口才重算。

### 5.4 目录整理（LLM，全量一次）

**看全项目全量，绝不只看待分类。** 只整理待分类会缺上下文，目录分派必然越整越歪。

能做到全量的关键是**这一步不看字段**。每个接口压缩成一行：方法、路径、一句话用途，约 20 token。
47 个接口不到 1500 token，500 个接口约 1 万 token，都放得下。
同时送当前目录结构，让 LLM 输出完整新结构与每个接口的归属。

小修（把待分类里几个放进现有目录）还是重构（目录划分已不合理，重新分）由 LLM 判断，用户不需要选。

依赖：必须在 §5.3 之后。若接口还没有一句话用途，LLM 只看到
`POST /gateway/gree-business-order-consult/consult-api/v1/manager/consultTechnology/page`，
分出来的目录与按路径前缀切没有区别。

### 5.5 写入与生效

开一个整理轮次，本轮所有名称、描述、目录、关联变更挂在该轮次上，并记录**变更前的值**（非全量快照）。
默认自动生效，不走人工审核。可按轮回滚，不做单条撤销（单条直接改即可）。

一轮约几十 KB：47 条描述变更 + 一份原目录结构。跑一百轮才几 MB，
所以修订历史本身不需要容量策略。真正需要容量策略的是 `fingerprints.sample`（见 §7.2）。

写入后目录树读模型刷新，待分类清空，左侧长出有名字的一级目录。

## 6. 目录与召回设计

### 6.1 形状由召回方式倒推

agent 的检索是四步渐进式披露，每步 token 预算可控：

1. **项目有哪些主题** —— 一级目录全量返回，每条是名称 + 一句话概括 + 接口数。
   必须小到可无条件全量返回（几百 token），因为 agent 还不知道该搜什么关键词，需要先看到地图。
2. **某主题下有哪些接口** —— 方法、路径、一句话用途，二三十条，一两千 token。
3. **单接口完整信息** —— 字段、类型、必填性、环境差异、关联接口。
4. **原始示例**。

倒推出的硬约束：一级目录数量 ≤ 12，最大深度 3 层（正常 2 层）。
限制深度不为好看，是为 token 预算可预测 —— 深度不封顶时 agent 要钻五六层，每层一次工具调用，慢且易迷路。

预期整理结果与 `/gateway/` 服务划分**不一致**，这正是整理的价值：
从技术部署结构翻译成业务语义结构（例：组织树接口在 `order-admin` 服务下，业务上属于「组织与人员」）。

### 6.2 一个接口只能在一个目录

渐进式披露依赖树的排他性。若一个接口能出现在三个目录，第一层的「接口数」失去意义，
agent 逐目录浏览会反复撞见同一接口，token 预算也算不准。树必须是真的树。
物理保证：接口位置表对接口 ID 加唯一约束。

跨领域召回的需求由**关联图**满足，不用多重目录实现。见 §5.2。

### 6.3 待分类是虚拟的

待分类不是存储记录，而是「observe 里有、knowledge 里没安排位置」这个查询的结果。
接口一被 observe 接收就**已经在**待分类里，无需额外写 knowledge —— 没有写入就没有失败、延迟和漏写。
做成真实目录反而多一个会出问题的环节。

代价：待分类不能重命名、不能手动拖入。可接受，它本就该是纯派生的收件箱。

## 7. 后续工作清单

按优先级排。演示（2026-09-30）当天都不做。

### 7.1 补采页面上下文 —— 最便宜、收益最大

`context.page_title` / `page_url` 让 LLM 从人类界面语言反推业务含义，一级目录会准得多；
`interaction_id` + `seq` 记录一次用户操作里按顺序发出的多个请求，直接给出
「哪些接口总是一起被调用」，这是目录聚类的最强信号（比路径前缀强得多），也是关联图的来源。

工作量：改 observe 的 ingest 与存储，加一张表。
代价：已采集的 47 个接口 context 已永久丢失，需重新采集才有数据。
这是目前唯一白扔掉的证据，应尽早做。

### 7.2 字段值样本收集

不是存更多整份示例（`getRootOrgTree` 一份几十 KB，容量涨得快），而是记录标量字段出现过的不同值，
每字段上限约 20 个，各带出现次数。容量只涨几 KB，却能：

- 写出完整枚举（「取值有中央空调、家用空调、热水器」）
- 标出「31 次里 31 次都是 null」这类事实
- 提高 §5.2 值匹配的命中率

与关联发现是同一件事的两面，应一起做。

### 7.3 关联发现的 LLM 环节

候选有歧义时判断方向（谁提供谁消费），以及把关系翻译成人话。

### 7.4 关联变化触发重算的增量失效

即 §5.3 的第三类失效条件。首次整理时所有接口都要补全，用不上；项目稳定后才是主要路径。

### 7.5 目录整理拆两段

约 300 个接口以上，一次看全量质量会下降。改成：先用抽样摘要问出一级目录结构（一次请求），
固定后把接口分批每批 100 个并行分派。仍是全局上下文，因为目录结构全局定。留好接口位置。

### 7.6 MCP 工具切到目录树

0004 §3 定的五个工具是按路径文字匹配的扁平检索，那是没有目录时的临时方案。
有目录后应直接做成 §6.1 的四步渐进式披露。
另需：access 里的 token 表（只存 hash）、创建/列出/吊销路由、设置页 token 区、
实现 `McpTokenVerifier` 替换当前恒拒绝的占位。

### 7.7 view 模块

**明天不建，这是对 0002 的偏离，已与用户确认。**
0002 让 view 负责算待分类和读模型，但待分类本质是一次集合相减，
为它单开模块加一层契约在一天内是负担。当前让 knowledge core 直接提供目录树读取，
接口清单从 observe 的 `EndpointReader` 拿，相减在 core 里做。
等到需要排序、搜索、向量召回时再引入 view —— 那时它才有真正职责。

### 7.8 容量与归档策略

针对 `fingerprints.sample`（真实请求响应，每种结构变化存一份）。
整理的修订历史不需要（见 §5.5）。

### 7.9 其它

- 人工审核开关：0002 明确「改成自动生效只是 knowledge 里一条策略的变化」，先做自动不挖坑
- 回滚按钮（后端路由明天就有，UI 后补）
- 单轮预算上限：超过就停，报告剩余量，下次继续，防大项目首次整理跑失控
- `types` 路径参数默认 `string`：放在前端展示层，日后 Swagger 声明可覆盖

## 8. 时长与请求数

单次整理的 LLM 请求数 = 需要补全的接口数 + 1。

| 场景 | 请求数 | 预估 |
|---|---|---|
| 47 接口首次整理 | 48 | < 3 分钟（并发 8，6 轮） |
| 500 接口首次整理 | 501 | 约 15 分钟（63 轮） |
| 日常整理（新增 10 个接口） | 11 | 一两分钟 |

**整理时长跟变化量挂钩，不跟总量挂钩。** 这是结构指纹缓存带来的，也是整个设计能撑住规模的根本原因。
目录整理那一步的成本增长是线性 token 而非线性请求数，所以始终是一次请求。

控时长的五个手段，按效果排序：结构指纹缓存 > 补全阶段并发（默认 8）>
目录阶段压缩摘要 > 超阈值拆两段（§7.5）> 单轮预算上限。

## 9. 明天的实施步骤

1. **knowledge 存储** —— 新建 `modules/knowledge/{contracts,core,adapter}` 与一张迁移。
   表：目录（项目、父节点、名称、概括、排序）；接口位置（接口 ID 唯一 → 目录，带来源与时间）；
   接口说明（名称、用途）；字段说明（接口 + 字段路径 → 说明）；
   接口关联（来源接口与字段、目标接口与字段、关系类型、证据、置信度）；整理轮次；修订（轮次 + 变更前值）。
   每张表写入都带作者与来源。
