# 服务重启后的整理恢复

2026-10-12 更新：任务入口与自动领取已由 [持久化任务队列](0018-persistent-curation-queue.md) 接续；本文保留原候选恢复设计背景。

2026-10-09。保持单后端和 PostgreSQL 部署，复用现有冻结输入、候选批次和执行租约。

## 用户行为

后端更新或异常退出后，已保存的候选内容保留。新 API 启动后自动检查原本仍为 running、但执行租约已经过期的任务，并继续同一个候选轮次。用户手动停止、普通失败后进入 partial/interrupted、已完成、已应用、已废弃的轮次不自动启动。

尚未保存完整恢复输入的准备阶段，或冻结资料不兼容、正式知识基线发生变化时，转为中断状态并保留明确原因；没有兼容恢复资料的任务由用户处理，不自动新建一轮。

正在等待模型回复但没有确认保存的批次可能重新调用。已经确认保存且仍适用的批次复用；不能保证模型请求的外部计费恰好一次。

## 边界与职责

- knowledge 公共候选端口提供轻量恢复扫描和受保护的接管；没有新增 HTTP 或 MCP 恢复入口。
- knowledge core 在项目事务锁内决定租约、状态和基线是否允许接管，写入新的执行 owner。
- knowledge adapter 只查询本模块的 candidates 表。扫描只返回候选和项目 ID，不加载大块冻结输入；按 ID 游标分页，部分索引仅覆盖 running 行。
- runtime 每 20 秒检查一次，启动时立即检查。恢复后使用现有 executor，重建已保存字段统计和待处理清单。
- API 装配负责启动和取消恢复循环；配置检查、迁移工具及普通 build_api 装配不隐式运行恢复器。

## 原子接管

沿用当前 120 秒租约和每 20 秒心跳。扫描只是提示，接管事务重新读取候选：

1. 必须仍为 running，且租约已过期。扫描之后发生的手动停止或心跳续约优先。
2. 必须有已保存输入，正式知识及接口集合仍符合原基线；项目内不能有另一个仍持有效租约的候选。
3. 接管沿用候选 ID、创建时间、冻结输入、已保存命令和最初发起人。旧 running 批次关闭为 failed，但已确认提交的命令保留。
4. 分配新的 run_id，记录由系统执行的 Resume 操作。旧 owner 的追加、关闭批次、心跳和状态提交均被现有 owner/state 校验拒绝。

runtime 接管后校验 FrozenInput 的结构和 version=2。格式不兼容时持久化 interrupted、recovery_blocked 和说明，关闭自动重试，避免循环调用模型。摘要和进度读取尊重这个阻断标记。

正式知识不由恢复器修改或应用。人工审阅、应用和废弃继续走原流程。

## 进度与记录

恢复使用同一候选，保留最初 started_at，追加新的 attempt。原执行的未关闭 attempt 标记 interrupted。按已保存批次重建字段数，活动批次重新计算，恢复过程写入“服务重启后，系统继续本轮整理”的动态。

系统身份只出现在实际恢复操作中，不新增静态系统占位；原发起人的操作记录保留。

原租约过期、等待恢复时，进度提示系统正在尝试续跑。缺少或不兼容恢复资料、正式基线变化的情况明确显示原因和已有内容保留状态。

## 发布

沿用现有流程：运行 `nexofolio-admin migrate`，再更新 API。新增迁移只增加 knowledge.candidates 的 running 部分索引，不增加队列或新服务。

自动续跑开始时间受剩余租约、20 秒检查间隔、数据库及模型服务可用性影响；120 秒不是整次恢复的完成时间。

## 验证

自动回归覆盖 120 秒边界、启动后等待再接管、扫描后的手动停止／心跳续约、游标分页、原始发起人和已保存内容、格式／基线阻断、旧执行权隔离和关闭取消。

隔离 PostgreSQL 使用真实事务测试并发接管；真实 API 进程测试在部分字段落库后发送 SIGKILL，再同时启动两个新实例，不调用 resume API，核对只补剩余字段且只接管一次。模型为本地固定响应服务，没有真实模型费用。进程测试将已终止测试任务的旧心跳回拨 121 秒，线上租约常量保持 120 秒。
