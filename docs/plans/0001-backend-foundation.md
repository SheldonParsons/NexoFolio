## 1. 实施目标与边界

以 Rust 为本计划的实现基线，建立可部署、可恢复、可验证的服务端基础架构。
通过 HTTP MCP 让 agent 浏览虚拟目录、查询接口、读取证据和提交变更。
后端仓库：`/Users/sheldon/Documents/GithubProject/NexoFolio`。
前端仓库：`/Users/sheldon/Documents/GithubProject/NexoFolio-Front`，前端选型和页面开发另行讨论。

首轮交付应能完整演示：

> 禅道验证登录与项目同步 → 接收浏览器流量并快速去重 → 保存新观测/接口 → 尝试已有分类 → agent 查询和读取 → 冲突进入待裁决 → 触发器形成检查/重构意图 → 构建候选 → 持续写入期间发布 → 重启恢复。

基础架构与目录效果分别验收。完成数据库、MCP 和 worker 的技术链路，不代表自动目录提升了召回。
首轮只开放 JSON/HTTP 接口记录，定义、来源与调用证据分别保存；其他协议和大型附件作为后续扩展。
优先实现有明确契约的 Chrome 插件批量采集 JSON；OpenAPI 导入随后接入相同知识处理能力，支持范围与不支持项必须明确返回。

## 2. 必须维持的规则

1. 正式知识集中存放在服务端，虚拟路径不对应个人磁盘路径。
2. 接口 ID 稳定；目录重分类不移动接口正文，不改变权限归属。
3. 新接口成功提交后可通过 ID、基础列表和词面搜索读取；模型归类、摘要和向量生成均不阻塞这条链路。
4. 每套目录独立维护归属。有效记录没有该版本下的有效归属时，出现在该版本的待分类视图。
5. 新接口优先尝试已有分类；分类依据不足时允许暂不分类。
6. 待裁决提案与正式定义分离。候选目录和自动摘要不得将未确认内容当作正式事实。
7. 数量可触发检查，不能单独决定全量重构；优先选择补摘要、增加别名、移动引用等局部修补。
8. 所有发布、修订和任务结果写入都有版本条件与幂等约束。
9. 删除、权限撤销立即作用于读取；旧目录、旧快照和缓存不能绕过当前权限。
10. 普通登录由禅道验证；超级密码可登录任意已有用户，不创建用户或增加其权限。项目权限跟随禅道，具体接入资料待提供，本轮只建契约。
11. 项目只能同步，任何入口均不允许任意创建项目。
12. 重复流量不产生逐条持久事件或触发重构；性能评估区分必要授权检查与数据判重成本。
13. MCP 使用独立管理入口签发的专用 Token，通过 HTTP Authorization 头传入；Token 不进入工具参数。
14. 普通禅道登录成功后创建或复用 3 个月有效期的内部 Token，并同步一次项目和该用户可见范围。有效 Token 原样复用且不延期；未来独立项目同步接口复用相同同步服务，仅验证内部 Token，不重新执行平台登录流程或刷新内部 Token。

## 4. 代码组织

采用 Cargo workspace，为业务边界设置独立 library package，提供 API、worker、管理 CLI 三个二进制入口。
CLI 包含迁移、禅道项目同步、导入与实验回放子命令，不提供任意创建项目操作。
完整内部目录、所有权与禁止依赖见模块化后端架构；这里保留工程骨架。

```text
NexoFolio/
├── Cargo.toml
├── Cargo.lock
├── rust-toolchain.toml
├── apps/backend/                 # api、worker、admin 入口和传输装配
├── crates/
│   ├── contracts/                # 跨模块 ID、事件和命令
│   ├── access/                   # 登录、用户、禅道项目同步规则
│   ├── knowledge/                # 接口、证据、提案、目录、检索
│   ├── intake/                   # 高频校验、身份、结构指纹与去重
│   ├── triggers/                 # 可替换触发规则与决策
│   ├── rebuild/                  # 重构规划、策略与评估
│   ├── application/              # 跨模块编排和事务/任务契约
│   └── infrastructure/           # 数据库、禅道、缓存、模型、队列实现
├── migrations/
├── tests/
│   ├── architecture/
│   ├── integration/
│   ├── mcp_http/
│   └── fixtures/
├── experiments/
│   ├── datasets/
│   ├── policies/
│   └── queries/
├── benchmarks/                   # 高频采集负载、基线和优化对照
├── deploy/                       # Dockerfile、Compose、配置示例
└── docs/
```

模块内部按需要增加 model、service、ports 等文件，不为每张数据库表机械生成多层类。
共享业务服务由 MCP、HTTP、CLI 和 worker 直接调用，避免通过内部 HTTP 请求复用自身逻辑。
领域类型不依赖 Axum/rmcp；数据库事务由一次应用操作统一控制，仓储方法不能各自偷偷提交。
传输 DTO、领域类型与数据库行类型分别承担协议、业务和存储职责。

第一批需要替换的边界：禅道身份与项目源、`ModelProvider`、`EmbeddingProvider`、`Classifier`、`TriggerPolicy`、`CatalogBuilder`、`CatalogEvaluator`、`SearchProvider`、去重缓存、任务派发和持久化事务入口。
`CatalogPublisher` 是受版本与权限约束的确定性服务，不允许模型直接修改发布指针。
生产适配器与离线实验适配器实现相同契约。

## 5. 数据模型和迁移批次

使用 UUID 等稳定身份字段；MCP 中可提供可读前缀，但不能以路径或自增序号充当跨版本身份。
接口稳定 ID 不绑定项目；项目/服务为可变归属，当前范围的去重键与永久身份分开。共享 Schema 和证据使用显式引用，为选择性导出保留依赖信息。

| 批次 | 表/概念 | 关键内容和约束 |
| --- | --- | --- |
| A：用户与项目 | users、external_identities、sessions、project_grants | 禅道身份映射、本平台会话、read/write/adjudicate/publish 权限 |
| A | mcp_tokens、mcp_token_projects/scopes | 独立凭证摘要、所有者、项目与读写范围、有效期及撤销 |
| A | projects、project_sync_runs、project_capture_bindings | 禅道唯一映射、分页覆盖与状态、服务/域名采集授权映射 |
| A | records | 稳定 ID、项目、服务、方法、规范化路径、API 版本范围、当前修订、删除状态 |
| A | record_revisions | 不可变正文、Schema 版本、作者、来源、创建事件序号 |
| A | sources、evidence | 来源类型、采集时间、原始资料/样例及关联修订；证据不等于定义 |
| A | observation_variants、capture_inbox | 已知结构变体、可靠接收与处理状态；高频相同观测不逐条写入 |
| A | project_events、outbox | 项目内有序变更、待派发事件、投递状态与重试时间 |
| B：变更 | change_proposals、idempotency_receipts | 基础修订、提议内容、冲突原因、裁决状态与操作回执 |
| C：目录 | catalog_versions、catalog_nodes | 目录结构版本、节点父子关系、范围说明、摘要依据、策略版本 |
| C | catalog_placements、path_aliases | 目录版本→记录 ID 的引用、归类所依据修订、主归属/交叉引用、旧路径映射 |
| D：构建与实验 | jobs、build_inputs、evaluation_runs | 输入快照清单、覆盖序号、执行代次、检查点、配置与评估报告 |
| E：可选检索 | record_embeddings | 记录修订、模型、维度、输入摘要哈希和向量 |

表名可在实现时调整，但身份、正式内容、导航关系和任务状态必须保持上述边界。
数据迁移按阶段新增，并通过空库和上一版本数据库两种路径验证。
对已发布迁移保持不可变；通过新增迁移修正。破坏性变更与数据回填单独安排。

### 接口去重和修订边界

- 初始匹配范围：项目 + 服务 + 方法 + 规范化路径 + API 版本范围。
- 路径参数优先来自规范定义；无法确定时保留原始路径并标记，不把所有数字段盲目折叠为参数。
- 同一身份、同一正式内容的重复导入返回 unchanged；新增调用样例不自动创建定义修订。
- 身份不确定或正式内容冲突时生成待裁决提案，不能直接合并。
- 获授权的显式编辑携带当前基础修订时可按业务规则应用；旧修订、来源冲突等进入待裁决。
- 裁决发生时再次检查基础修订；期间又有更新，提案转回待处理并注明原因，不覆盖新内容。

## 6. 一致性实现

### 写入与事件

需要持久化的新知识或变更在短事务内完成身份/基础修订检查、修订或提案写入、项目事件和 outbox 写入、幂等回执保存。已处理的相同观测可直接忽略，不为每条流量分配项目事件序号。
项目事件序号通过项目行上的事务内递增值分配；不能仅以序列 MAX(id) 代表已提交边界。
幂等键按调用者、项目、操作隔离；相同键不同请求内容返回明确错误，相同请求返回原回执。
外部模型调用不得放在持有项目写锁的事务内。

### 新接口和待分类

新接口记录提交后，基础列表和词面搜索直接读取知识数据，不等待异步索引。首次观测记录标明 observed；仅获得 accepted 的输入以 ingestion_id 查询状态，不宣称已经生成正式接口定义。
归类任务先查看已有目录的范围摘要和代表接口，生成归属建议，并校验节点存在、项目范围和输入修订仍然有效。
待分类是“当前可见记录减去该目录版本下有效归属”的视图。修改导致旧归类依据失效时，标记待复核并安排增量处理。
正式目录和候选目录独立消费变化；某一版本分类成功不能隐式修改另一版本。

### 构建与发布

1. 在一致数据库快照中取得项目事件边界和记录修订 ID 清单，持久化为构建输入后结束读取事务。
2. 后台基于清单生成候选，所有长时间模型调用在事务外执行。
3. 按顺序补充快照后的变化，记录已连续处理到的覆盖位置；不能跳过失败事件后抬高水位。
4. 结构和归属检查通过后，针对候选最终输入版本运行评估。评估之后若修改了候选，至少重新验证受影响范围。
5. 使用正式目录版本、候选状态及有效执行代次做条件更新，原子切换目录版本和覆盖位置。
6. 尚未覆盖的新增/修改/删除继续由增量视图处理，候选无需追到没有新写入才能发布。

读取当前知识时按稳定 ID 合并目录引用和增量；数据源是正式记录，目录不能复活已删除内容。
目录结构版本、知识修订与一次读取快照分别标识。分页游标绑定项目、过滤条件、目录版本和读取快照；保留期内保持顺序稳定，过期明确要求刷新。
首轮可用短期服务端结果快照保存有序记录 ID/修订清单；每页仍校验当前权限与删除状态。
读取默认取当前修订，需要历史内容时显式传入 revision。回滚只切换导航版本，并重新叠加该版本尚未覆盖的事件。

### worker 恢复

任务状态：queued → running → succeeded / retry_wait / failed；取消单独记录 cancelled。
每次有效领取具有新的执行代次和租约/框架等价机制。提交检查点和结果时必须验证仍持有执行归属。
按“任务 ID + 步骤 + 输入版本”去重；模型输出可暂存，但超时或强退不能保证外部模型只计费一次。
明确设置有限重试、退避和终止条件；后台任务失败可查询，不能一直表现为正在处理中。
每个项目同一范围至多一个有效构建执行者；其他事件累计为增量。首轮可将范围收紧为每项目一个构建任务。

## 7. HTTP MCP 与管理契约

`/mcp` 使用 Streamable HTTP，由 rmcp 处理协议。支持哪些客户端版本以锁定 crate 的实际能力和连接测试为准。
虚拟资源 URI 使用服务自身命名空间，例如 `nexofolio://projects/{id}/records/{id}`，不向 agent 暴露服务器磁盘路径。
agent 的核心知识访问能力通过工具可达，资源呈现作为补充，避免依赖某个客户端自动注入目录。

| 工具 | 初始输入 | 返回重点 |
| --- | --- | --- |
| list_projects | query、cursor、limit | Token 当前可访问项目及根入口 |
| list_directory | project_id、directory_id、catalog_version、cursor、limit | 节点范围、摘要、一层子入口、待分类入口 |
| search_interfaces | project_id、query、directory_id、catalog_version、method、service_id、limit、cursor | 接口卡片、匹配依据、覆盖说明和稳定 ID |
| read_interface | project_id、interface_id、view、revision、max_chars、cursor | overview/definition/examples/history、来源、版本和续读 |
| create_interface | project_id、definition、source_ids、reason、idempotency_key | draft 新建、重复或冲突提案回执 |
| update_interface | project_id、interface_id、base_revision、changes、source_ids、reason、idempotency_key | applied / pending_adjudication / unchanged 及回执 ID |
| get_change | project_id、change_id | 当前状态、冲突依据和关联修订 |

工具名为本项目建议，不是 MCP 协议内置名称。
将 Schema 描述、实际校验、示例和契约测试放在一起维护。
需要裁决、触发构建、比较候选、发布/回滚的管理操作先由受权限控制的 CLI/HTTP 提供，不默认加入普通 agent 工具列表。

结果字段统一定义：request_id、项目/目标 ID、相关版本、来源、complete、truncated、next_cursor；没有意义的字段可省略。
业务错误统一为 VALIDATION_ERROR、NOT_FOUND、FORBIDDEN、STALE_REVISION、STALE_CURSOR、IDEMPOTENCY_CONFLICT、RETRYABLE_FAILURE 等，再由适配器映射传输格式。
进入待裁决是成功记录了提案，不应伪装成网络错误或自动触发重复提交。

后续普通用户经禅道验证后获得平台会话，独立 MCP Token 管理入口使用会话签发/列出/撤销凭证；插件使用自己的采集授权。超级密码分支按已确认的“任意已有用户”实现，不调用禅道。本轮仅有相关契约，MCP 默认拒绝全部凭证。
首轮签发者只能授予自己有权访问的已同步项目，默认只读。MCP 执行时校验凭证及当前权限，目标客户端的预配置 Bearer 支持需在 P0 验证。
HTTP/MCP/CLI 共用权限检查；目录摘要、搜索和证据读取也应用同一范围过滤。
面向更广泛公开客户端的 OAuth 接入单独实施，不能把实验令牌方案宣称为完整远程 MCP 授权兼容。

## 8. 实施阶段与完成条件

所有阶段默认直接开发，不自动创建子 agent。下面是后续实施顺序，本次仅交付计划。

| 阶段 | 工作与交付物 | 依赖 | 完成条件 |
| --- | --- | --- | --- |
| P0：依赖与模块边界 | 初始化 workspace、独立业务包与 ports、依赖白名单、Axum+rmcp 最小服务、SQLx/任务恢复试验 | 无 | 可编译；禁止依赖可被 CI 检出；真实 HTTP MCP 调用成功；任务框架恢复试验有结论 |
| P1：用户与项目基础 | 三入口、配置/日志、禅道身份 port、本平台会话、项目同步、专用 MCP Token 签发与访问控制 | P0 | 项目只能同步；部分同步不删除；普通/应急认证分开；Token 不可越权签发、可撤销，跨项目读取被拒绝 |
| P2：知识与采集基线 | A/B 批迁移、intake 批量入口、身份/结构指纹、已知变体、可靠接收、修订/提案/裁决 | P1 | 重复观测不重复写入；变化不漏判；旧修订不覆盖；建立热/冷缓存与混合负载性能基线 |
| P3：目录与 MCP 闭环 | C 批迁移、现有分类匹配、待分类、分层读取、词面搜索、七个工具及 Schema 契约 | P2 | 专用 Token 调用成功；只读/写权限分开；agent 找到正确接口及证据；归类后退出对应待分类视图 |
| P4：独立触发与重构 | triggers/rebuild 契约、事件合并、持久任务、快照/增量、候选评估、发布和回滚 | P2/P3 | 新增触发规则不改 intake；新增策略不改登录/传输；持续写入可发布；旧 worker 不可发布 |
| P5：组织策略实验 | 可配置策略、模型适配、固定/数量/局部调整三组、查询回放和报告 | P4 | 使用同一输入和查询完成对比；记录成本和失败案例；得出发布策略的保留/调整结论 |
| P6：Linux 交付 | 多阶段 Dockerfile、Compose、配置模板、独立迁移步骤、运行与恢复说明 | P4；效果报告依赖 P5 | 目标架构容器启动并通过 HTTP 验收；数据卷重启后保留；数据库迁移与程序版本相容 |

每阶段保持主链路可演示。P0 的 PostgreSQL/任务试验使用隔离数据，不要求现有生产服务提供资源。
P3 可以先使用规则和固定响应模型替身验证工程链路；P5 需要真实模型和真实 agent 数据，不能用替身得出效果结论。

## 9. 验证矩阵

| 层次 | 重点用例 | 证据 |
| --- | --- | --- |
| 领域单测 | 身份匹配、状态转换、去重、目录边界、发布条件 | cargo test 结果 |
| 架构约束 | 业务包依赖白名单、私有实现、触发/重构替换 | cargo metadata 依赖检查和独立契约测试 |
| 禅道集成 | 普通登录、应急分支、完整/部分项目同步、身份与权限映射 | 版本化适配器测试；真实禅道验收单列 |
| 高频采集 | 重复/新结构混合、冷热缓存、多实例、报文大小、队列压力 | P50/P95/P99、资源占用、SQL 次数、漏判与误判、可见延迟 |
| PostgreSQL 集成 | 并发修订、原子事件、幂等、迁移、权限隔离、分类引用 | 隔离真实 PostgreSQL 测试与数据库断言 |
| worker 故障 | 领取后强退、重复投递、租约过期、检查点恢复、旧执行者晚到 | 任务历史、最终状态与发布记录 |
| HTTP MCP | 真实网络请求、列表/读取/搜索/修改、错误、分页、限长、授权 | 协议记录和契约断言 |
| 持续写入 | 候选构建/评估/发布期间新增、修改、删除、提案裁决 | 逐事件回放与记录覆盖检查 |
| agent 效果 | 名称查询、业务表达、字段定位、跨目录、冷门、新接口、无答案 | 正确接口/证据覆盖、工具调用、读取 token、耗时、回退与成本 |
| 部署验收 | Linux 目标架构启动、证书、迁移、重启与健康检查 | 镜像版本、执行命令、验收输出 |

查询集分为策略调整集和留出验证集；以相同数据时点、工具权限和预算对比目录策略。
目录生成使用的模型与实际查询 agent 分别记录；可重复运行估计波动，不能把一次随机成功当作改善。
初始样本规模建议 30～100 个接口，覆盖至少三个业务主题及易混淆目录，规模可随真实数据调整。
自动发布首先要求无丢记录、无断引用、无权限回退，并通过保留查询集的质量检查；收益阈值由 P5 的实测结果决定。

实施后建议执行：`cargo fmt --all --check`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo test --workspace --locked`，再运行架构依赖检查、真实 PostgreSQL 与 HTTP MCP 集成套件。
使用 SQLx 编译期查询宏时，应生成并检查离线查询元数据，同时保留真实数据库迁移测试；不能只依赖离线编译通过。
测试报告必须区分已执行、未执行及受外部条件阻塞的项目。

## 10. Linux 交付与运维基础

- 在匹配目标 CPU 架构的 Linux 构建环境生成版本固定的程序和镜像，核实运行库依赖；不直接部署 macOS 构建产物。
- API 和 worker 使用同一版本的镜像，分别执行不同二进制；PostgreSQL 使用独立持久卷。
- 数据迁移由单独命令或一次性容器执行，避免所有 API/worker 启动时并发迁移。
- liveness 反映进程存活，readiness 检查数据库和必要 Schema；模型提供商暂时不可用不应使基础读取退出服务。
- 每次请求/任务记录 request_id、job_id、project_id、目录版本和耗时；默认不打印令牌或原始请求响应正文。
- 配置控制连接池、模型并发、单任务预算和输入大小；慢任务放到 worker，通过任务 ID 查询结果。
- 记录程序、数据库 Schema、目录策略和模型配置版本；应用回滚先检查数据库兼容，目录回滚只处理导航视图。
- 提供备份与恢复步骤，并在隔离数据库上验证至少一次恢复。
