## 2. 测到的具体问题

### S1：抽取预算不一致会产生不可靠的unchanged（修复判定问题）

`intake/http_exchange.rs`对每个JSON body最多100000节点；`knowledge/observed.rs`共享10000节点预算。实际录制的最大单个JSON为17430节点，深度9，已超过后台预算。

派生样例：响应前部为超过10000节点的数组，尾部字段z从number变string。入口有完整projection，识别为不覆盖；后台两次都抽取到相同前缀、丢掉z，因为`definition_covers`先判断整体相等再检查STRUCTURE_EXTRACTION_LIMIT，结果为true。完全相同的truncated/unreadable观测也会返回true。

这没有丢掉原文或自动覆盖当前定义，但“无法比较”被折叠成了unchanged，不符合本阶段预期。不能只把预算调大：任何有限预算都可能耗尽，必须修正未知的表达和判定。

### S2：一个null导致整个快速指纹失效（性能与能力优化）

153条真实HTTP中69条没有结构projection，其中68条JSON含null，另1条为不可读的文件上传体。入口shape遇到null就返回None，向上传播到整棵树；因此相同含null的记录不能利用快速结构去重，后台又可能判unchanged。

需要区分“完整读到了null这个值”和“正文/子树根本没读到”。null不建立具体业务类型，但不应抹掉整份完整JSON中已观察到的结构。首次nonnull出现仍须交给后台解释为补充信息，不能被指纹吞掉。

### S3：只有布尔值，没有四类解释（新增能力，非原文错误）

共享函数和knowledge比较都返回bool；`PostgresDocuments::finish`把非覆盖统一写为difference_recorded。无法表达同一条观测同时有补全、明确观察差异与不足。

现有8条都保持pending，没有覆盖当前定义。测试证明旧行为可复现，并不证明四类判断已实现。

### S4：新观测字段缺乏稳定的下游身份（跨模块合同缺口）

用现行`snapshot_fields`得到1640个当前字段。299条observed_value事实涉及52个不同字段引用，不在当前定义索引中。资料仍保存在原文和facts里，不能说已丢失；但不能把它们当作已存在于当前修订的字段。

原因与后续阶段有关：阶段1不自动采用补全/差异，阶段2现在常以compared_revision_id绑定观测字段，阶段3按当前定义生成字段索引。若阶段1只加分类字符串，后面仍会回来索要新观测结构、来源和未确认字段定位。

### S5：两份提取算法、三处比较/路由职责（收敛重复实现）

intake和knowledge各有shape/body/media/header处理；共享比较函数上面又各包了一套完整性和元信息判断。预算和null差异已经证明这不是纯风格问题。应收敛共同结构解释，同时保留入口准备、文档展示和事务各自必要职责。

## 4. 推荐模块设计：一套规则，明确边界

不新增业务服务或Cargo包。依赖方向仍为核心包仅依赖contracts。

### 共享基础（contracts）

在现有observed_comparison基础上，集中基本JSON形状及覆盖规则。共同输出包含schema与有来源的局部unknown/覆盖缺口；区分null、空数组、采集不可读、解析失败和抽取预算，而不是都用同一个unknown/None。

只放无IO的结构表示和纯函数；不把数据库、HTTP权限、LLM或目录策略搬进contracts。URL、媒体类型和已有回执哈希的适配职责仍由各自边界承担，避免为了少几行把所有模块揉在一起。

### intake：快速决定是否需要结构处理

返回“可确定已覆盖”或“交给后台”，不生成庞大解释报告。相同含null形状能够稳定比较；无法证明覆盖时继续入队。保持项目/环境/接口身份规则，不改变路径模板算法，不扫描历史，不调用模型。

结构指纹算法版本独立升级，只在需要时更新当前head；旧record/batch内容、content_hash及幂等回执不改写。不新增独立缓存服务或另一套指纹算法。

### knowledge：唯一详细分类器

纯函数输入“比较基准、新观测结构、覆盖信息”，返回逐字段发现；与intake共享基本规则。输出可以同时含补全、差异和缺口，保留一个总体摘要用于列表。

当前定义的字段与“本次新观察到但尚未纳入当前定义的字段”分别定位。首次见到接口继续走created生命周期，不硬塞进四种比较结果。

### infrastructure/application：提交结果与提供资料

维持现有事务、幂等、租约和同接口顺序。事务内拿到真实当前基准后调用knowledge纯函数；数据库层只按结果保存，不再自己决定什么算补全/变动。

优先在现有observation结果上保存稀疏assessment（类别、原因、字段片段、覆盖缺口和来源），复用原文及已有proposed_definition，避免给每个消费者复制完整文档。明确新增的读接口，不把内部数据库表结构作为阶段2/3的合同。

不自动采用补全、不自动裁决、不改当前修订。读取可通过独立assessment资源扩展，保留现有上传回执及旧读取形状，避免本轮拖入前端布局修改。

## 5. 阶段1必须交付的消费合同

这是减少后面返工的关键，不等到阶段3再设计。

| 内容 | 必须表达的意义 |
| --- | --- |
| 身份 | project、environment、interface；新接口允许尚无比较基准 |
| 版本 | comparison_rule_version、extractor_version、base_revision_id |
| 输入来源 | 真实capture observation/ingestion引用；原文与捕获完整性可查询 |
| 总体结果 | 是否可安全跳过重复结构处理、各类发现和未读范围；不把“处理完成”当成“信息完整” |
| 字段发现 | location/path、类别、原因码、前后结构片段、来源，不只有中文字符串 |
| 未确认字段 | 使用“观测来源＋字段路径”定位，不伪装成当前修订已包含的FieldRef |
| 读取边界 | 可按项目/接口/环境读取稳定结果；缺失/过期/无权限明确返回，不临时重算另一套规则 |

阶段2消费“字段观察＋来源＋不确定性”，阶段3消费“当前结构＋补全/待确认资料＋覆盖信息”。阶段3可以新增自己的快照装配器，但不要求阶段1改分类含义或重新接收数据。

要加两个小型消费契约测试：证据消费者能定位未确认字段；快照消费者能读到补全与缺口但不会把它们冒充当前正式字段。此阶段验证端口，不实现完整阶段2/3业务。

无法保证今后新增需求绝不改代码；可以要求本阶段已约定的接口和含义冻结，后续扩展走明确版本变更，避免无意返工。

## 8. 实施顺序与阶段出口

1. 先确定并生成assessment合同及语义真值表（包括空值、缺失、预算、混合发现、响应状态/媒体变化），配消费契约测试。
2. 合并结构提取与比较基础，替换intake/knowledge重复实现；先过16组边界及当前已记录失败模式。
3. 接入结果持久化/读取，保证原始回执不变、原基准不覆盖；必要迁移在隔离快照验证。
4. 再跑153条真实HTTP回放、原始字节/幂等/并发隔离、8条分类前后对照、两种下游消费者和架构检查。
5. 提交逐文件实际增删统计与保留/删除理由，完成阶段1评审后才考虑阶段2。

阶段1完成条件是“分类正确＋稳定消费合同＋旧数据/幂等保护＋代码收敛有据”，不是仅把本模块单测跑绿。不会在完成后自动进入后续阶段。
