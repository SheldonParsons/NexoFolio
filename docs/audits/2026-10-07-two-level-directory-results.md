# 两层目录：实施与证据

2026-10-07，主会话直接实施。**后台已具备生成、校验、保存和更新两层目录的能力；没有对真实商业项目重新整理，也没有宣称真实页面已变成两层。**

## 改了什么

旧实现让模型返回一层目录，按路径片段命中接口，先命中者占用。旧目录改名还可能复用无关的第一个目录，并删除没有复用的子目录，破坏链接。

新实现让模型读取完整接口语义及旧归属，明确返回业务模块→功能分组→接口编号。代码独立校验，不把模型建议直接当数据库指令。两层限制在知识写入层也执行，第三层不能新建。

旧目录 ID 根据明确旧引用、名称或完全相同成员复用，改名/移动不换 ID；不能把已有链接借给完全不同的业务成员。旧目录不自动删除，接口归属有改变才写入。人工目录与归属、无法确认来源的旧元数据受保护，提交前再次检查，避免模型处理期间的人工编辑被覆盖。

目录作者新增后，保存和回滚同样记录作者；旧历史回填采用保守规则。没有改旧迁移文件、没有另造一套目录存储。详见 [结构与规则](../architecture/0010-two-level-directory-curation.md)。

## 能证明的收益

在真实隔离 PostgreSQL 中，用固定模型与构造的 4 个接口元数据演练：

| 项目 | 改前 | 改后/复核结果 |
|---|---|---|
| 目录层级 | 2 个一级目录，接口直接挂一级 | 2 个业务模块 + 4 个功能分组，接口挂二级 |
| 旧一级链接 | 2 个旧 UUID | 两个 UUID 全部保留 |
| 归属 | 4 个接口挂一级 | 4 个接口各有唯一二级归属，一级统计正确累计，接口读取返回完整父子路径 |
| 重复整理同一结构 | 旧实现仍生成目录和归属写入 | 新流程产生 0 条更新命令 |
| 改名 | 依赖旧名或任意替换旧身份 | 真实保存模块/分组新名称，UUID 和接口归属不变 |
| 同名子目录移动 | 新实现必须处理 SQL 同层唯一约束 | 两个“查询”分组移到不同模块，ID 保持不变；临时名不会出现在提交结果，回滚完整恢复 |
| 旧三层历史 | 原知识规则允许 3 层 | 已知生成记录转为两层，3 个旧 ID 都保留；还能回滚恢复旧形态 |
| 并发人工编辑 | 模型使用较早快照 | 提交时发现新人工修改，拒绝自动覆盖；同批较早写入也一起回滚，人工名称/归属/作者保留 |

这证明的是后台处理能力和数据一致性，不是模型对真实 47 个接口的业务分组已经全部正确。目录编号、名称与介绍的真实质量留在最后的实际项目验收。
