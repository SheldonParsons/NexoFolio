# 商用订单管理系统：整理数据调查与优化方案

调查日期：2026-10-07（Asia/Shanghai）。范围为项目 `57a3a86b-2fe4-4d4e-95b9-64a1a086b7a7` 的当前保存数据和生成实现。数据库采用只读查询；本轮没有重新运行模型整理或改写知识。前端对象数组行的局部改动单独记录在 §8。

## 1. 结论与调查边界

现有整理已经提供可用的基础说明，但尚未充分利用已保存的语义线索。主要问题是：目录生成固定一层；部分说明过于宽泛或错误；关系规则漏掉异名参数传递和配置对应，同时保留大量通用值匹配。

不是所有名称、说明都需要重写，也不是每个接口都应有关系。优化依据应是已采到的原始信息及明确标注的推测。不能把未知状态码补成假枚举，也不能把相关接口解释成必须先调用的接口。

本轮逐一检查 47 条接口名称/用途，对全部字段记录做完整性、重复和证据统计，并深入核对组织、咨询、审批、认证、字典、列配置、订单和非标配置的字段、结构、值、页面及调用顺序。没有逐条证明 1,738 个字段的全部业务含义。

## 2. 目录：属于实现限制

三个位置共同限制了结果：

1. `curate/core/src/interpretation/prompt.rs` 只要求 3–8 个顶级文件夹。
2. `FolderSpec` 只有 name/summary/match，没有父子关系；生成命令固定 `parent: None`。
3. organizer 会移除未复用目录，包括既有子目录。只手动创建子目录不能解决自动整理的问题。

存储与 knowledge core 本来支持父子目录，但公共 `MAX_DEPTH` 目前为 3，不是用户要求的最多两层。前端 `useDocumentProject` 把所有文件夹平铺为 sections，`InterfaceList` 没有父子目录呈现；父目录自身没有接口时还会被过滤掉。

建议：统一“两层”为业务模块 → 子分组，接口位于第二层目录内。生成、校验、差异写入和前端展示一起调整。参考分组：

| 第一层 | 可用的第二层分组示例 |
|---|---|
| 认证与权限 | 登录与验证；组织与用户；菜单权限 |
| 商品与配置 | 分类与选品；非标点配置；购物车 |
| 技术咨询 | 发起与校验；查询与详情；任务处理；报表与进度 |
| 订单与商机 | 订单查询；项目信息 |
| 流程与消息 | 审批操作配置；流程与待办；消息与公告 |
| 通用配置 | 地址与字典；页面列配置 |

这是基于当前接口的分组示意，不是已落库方案。已有可读的分类名称可以保留。目录应通过明确 endpoint ID 归属生成，避免仅按路径片段“先匹配者获胜”。提交前校验层级、重复归属、缺失归属；依据旧目录计算差异，保持可回滚。搜索需展开命中接口的祖先目录，默认展示和当前选择也需支持逐层展开。

GET `/` 的样本返回 text/html，出现在登录页面；不应为了消除待分类而编造业务目录或服务入口。先保留为页面/资源观测或待辨别项。

## 3. 接口名称：多数能保留，主要补区分信息

多数名称能表达动作和对象，例如“校验派单规则”“保存并提交技术咨询”“获取用户菜单”。不用为了统一措辞改写所有名称。

当前有三组重名，均与客户端/管理端区分有关：

- 两个“完成技术咨询任务”。
- 两个“查看技术咨询详情”。
- 两个“获取未读公告数量”。

建议按动作 + 对象 + 必要范围命名。对确有用途差异的接口加“管理端/供销云端”等范围；范围来自路径和采样场景，不自行推定具体用户角色。认证接口“格力业务订单认证令牌”可改为“获取登录访问令牌”，便于识别动作。

`file_upload` 接口读取审批操作配置。名称“文件上传审批模板列表”容易让人忽略其操作选项、意见和附件要求；可采用“查询带附件审批操作配置”等名称。不能把它描述成上传文件的接口。

## 4. 接口描述：增加输入、产出和场景，不增加无依据的规则

当前提示词只提供 method/path 和前 10 个字段及类型，要求用途不超过 30 字。实际值、页面上下文、主要响应结构、跨接口对应关系没有充分进入输入。字段多的接口，前 10 项可能全是请求字段，响应主要内容被遗漏。

可保留简短用途用于列表，在详情和 MCP 记录中另提供有依据的输入/输出/观测场景/关联说明。不必把所有内容塞进一个大段落。

| 接口 | 当前不足 | 有依据的补充方向 |
|---|---|---|
| 表格配置 find/{id} | “根据ID获取具体信息”过泛 | 读取某页面的用户列配置，包含标题、顺序、宽度、显示、固定和滚动设置；两份非空样本中参数等于 tableConfigCode，不等于数据库 data.id |
| 管理端 completeTask | “处理并完成流程任务”过泛 | 提交当前工作流任务的处理信息，可携带技术回复和报价明细；不宣称整条咨询流程结束 |
| 供销云端 completeTask | 与管理端重名、缺少场景区别 | 当前样本提交审批操作及任务信息；技术回复字段在该样本为空，不要求每次都有回复或报价 |
| 技术咨询详情 | 只说“根据ID查询详情” | 管理端响应聚合咨询主单、明细、回复和报价；路径 ID 对应 consultTechnology.id，不是 technologyItem.id |
| 技术咨询报表 | 写成“待技术审批” | 可说明申请时间等筛选和咨询/流程进度输出；当前样本不足以证明仅返回待审批数据 |
| 审批模板 | 只说“模板明细” | 返回同意/驳回操作、意见及附件配置；file_upload 的 isUploadFile 为 true，uploadFileIsRequired 为 false |
| 非标点新增 | 基本用途已经合理 | 请求确实含 configs 及 addMaterials/reduceMaterials 键，但当前增减数组为空；可说明返回 success/failList，不能补出未观察的材料明细结构 |
| 派单规则校验 | 基础用途已较准确 | 输出校验结果、失败品类路径和失败信息；校验不通过属于已观察到的业务分支 |
| GET `/` | “基本信息和可用入口”缺证据 | 当前只确认是 HTML 响应；不把可用入口作为已知功能 |

新增说明要区分“样本中出现”“根据结构推测”“有声明或配置依据”，特别是错误结果、必填条件、调用先后、适用角色和状态范围。

## 5. 字段：原始键名、中文显示名和完整描述分别处理

英文 JSON 键名是接口合同的一部分。可以加中文显示名和解释，但不能由整理更改真实请求键名。当前 FieldNote 只有 text，没有独立的中文名称/别名，短说明同时承担翻译和解释，难以容纳业务上下文。

全量字段中有 159 条说明写了“待确认”。有些保留不确定性是正确的，有些可以用现存证据进一步解释。不能用“待确认的条数下降”作为成功标准。

| 字段/位置 | 当前说明 | 调查依据与建议 | 确认边界 |
|---|---|---|---|
| 咨询分页 data.records[].itemCode | 物料条目编码 | 两个相关页面配置均把此字段标为“咨询子单号”；20 条记录的 itemCode 都在主单 code 后追加子编号 | 页面标签和样本关系可用，不能推广到所有接口的 itemCode |
| data.records[].estimatedAmount | 预估金额 | 页面列标题为“预计金额（万）”/“项目金额（万）” | 单位“万”有直接依据，币种未知 |
| participationMode | 参与方式，待确认 | 咨询页面列标题为“总部参与方式” | 可以补业务名称，数值 4 的具体含义仍未知 |
| categoryNameList / modelList | 分类名称列表/型号列表，用途待确认 | 对应列标题“产品系列”/“产品型号” | 作用于该页面/相关实体，不能全局覆盖同名字段 |
| 非标新增响应顶层 code | 编码，具体业务含义待确认 | 与 msg/data/popupType 同级的响应信封字段 | 可解释为业务响应码，不能拿它当商品编码 |
| 报价请求 technologyReplyPricingDTOS[].code | 编码 | 与同条记录 commodityCode 相同，与 Baan 响应 commodityCode 相同，型号及单位也一致 | 支持商品/物料编码对应，不构成必须先调用 Baan 的约束 |
| 报价 qty / unit | 数量 / 单位 | 所在对象是报价物料明细，可补“报价明细数量/计量单位” | type = "3" 的业务分类仍未知 |
| getRootOrgTree 的 children[].parentId | 父组织节点ID，关联来源待确认 | 本次树中 327 组子节点的 parentId 等于直接父节点 id | 可记录当前树内父子对应，不等于发现一个跨接口依赖 |
| technologyReplySjbVO 等 | “设计部”对象/列表 | 原始字段只是 Sjb，现有材料未证明它代表设计部 | 撤回无依据的缩写展开；保留技术回复相关对象，部门简称待确认 |
| 新增咨询的 consultPrice | 咨询价格 | 详情中同类明细字段为 boolean、值为 false；新增中为数值 0 | 更像是否咨询价格的标记，可以明确为推测；0 的编码含义和类型转换规则仍需验证 |
| getRootOrgTree 的 isCustomerOrg / isNextOrg | 是否客户组织/是否有下级组织 | 前者出现 0/1/2，后者出现 1/2 | 不把数字编码当 boolean，不臆造每个值的含义 |
| 组织树 userList | 用户列表，具体业务待确认 | 该公司组织接口目前只观察到 null | 基础含义可推测，实际元素结构和必填性保持未知 |

中文列配置确实在原始业务接口响应中，非 NexoFolio 上次整理生成。两份非空配置共 54 列；通过当前数据验证，44 个 column.code 与对应业务字段英文名的 SHA-256 一致（18 + 26）。这是当前样本的编码关系，不是所有产品、配置或接口的通用协议。

根组织接口有 157 条字段路径，children 路径展开到 13 层。重复节点说明会造成阅读和生成成本。可逐步引入“组织节点”的可复用结构描述，同时保留具体路径、深度差异、空数组和可选字段；不能直接删去深层观测，或把目前观察到的节点形状当成固定合同。

## 6. 关系：既有漏报，也有弱匹配

### 6.1 当前规则真实做了什么

693 条候选线索来自同环境的同名同值匹配，不只是同名。当前证据展示缺少匹配值和源字段位置，读者很难看出“值相同”的依据。

其中 190 条落在 msg、size、sort 三个低信息字段上（27.4%）。12 个接口的候选仅来自这些字段。它们不应被当成接口存在业务关联的证明。

匹配器排除了 id/code/status/name/type 等通用名，这有助于控制噪声，但也令有明确语义的 id → 路径 id、type → actionType、code → commodityCode 无法通过。最多保留前三个候选来源，前面的弱候选还可能挤占可用位置。

所有候选没有 value/label 选项；knowledge.links 为 0。因此“44 个接口有候选”不能理解为已建立可供 MCP 使用的接口关系网。

### 6.2 已找到、可以客观记录的更多关系

| 关系 | 原始样本证据 | 当前适合记录的含义 |
|---|---|---|
| 验证码字段传递 | gen.data.uniqueId = check.request.id = token.request.sliderCaptchaId；同一 page_id，seq 2 → 3 → 5；另一登录样本不匹配 | 记录这次样本的值传递路径，保留异名字段、页面与顺序；不宣称所有登录都必须此链路 |
| 咨询列表 → 详情 | 列表某条 records[].id 与管理端 detail/view 和供销云详情的路径 id 相同；管理端路径匹配主单 id，区别于明细 id | 记录带实体范围的列表到详情对应 |
| 待办 → 任务处理 | taskId 和 processInstanceId 同时匹配，同一页面且待办请求先发生 | 当前任务处理使用了待办返回的任务身份，不推定全部流程的硬依赖 |
| 模板选项 → 操作类型 | default/file_upload 都返回 type 1/name 同意、type 2/name 驳回；三个任务处理样本通过 taskId/processInstanceId 对应到相应 formKey，actionType=1/actionName=同意 | 可说明“该 formKey 的当前模板选项”，并记录 type → actionType 的作用域 |
| 条件配置 | 两个模板中“驳回”的 approvalCommentIsRequired 为 true；file_upload 允许附件但未标为必填 | 记录模板对当前操作的配置；未验证后端缺意见时必然拒绝 |
| 报价 → Baan 商品 | code/commodityCode 相等，同时型号和单位相等 | 多字段一致的物料对应，强于孤立同值 |
| 生产代码查询 → 非标新增 | productionCodeId、commodityId、commodityModel 三个字段一致；同页面 seq 9 → 10 | 记录本次新增使用了已查询的商品/生产代码信息 |
| 非标选项 → 新增 configs | 列表 id/name 与请求 configId/configName 一致；同页面 seq 7 → 10 | 支持异名配置选择映射；当前选中项在 20 项列表中的索引 19 |
| 节点内父子 | children[].parentId 等于其父 id | 树内关系，不是跨 API 的调用关系 |

最后一项非标选项被当前数组“只取前 12 项”的标量提取器遗漏。这是已采集证据没被利用，并非需要扩大采集。应把规则匹配的索引和发给模型的有限摘要分开：先匹配目标值、选择相关对象和标签，再控制模型上下文大小。

### 6.3 已知字典与尚未确认的适用关系

字典 select 的请求为 `dictCode=activiti_approval_status`，响应中直接存在：0 待审批、1 审批中、2 已通过、3 已驳回。这组 value/name 是已采到的信息，但本项目样本未建立它与具体消费字段的明确绑定。

技术咨询列表 status 实际出现 90/124/130/165。不能把审批字典强行套给它。saleType 1/2/3、consultType 1/2、participationMode 4、configStatus 1/2 等也不能仅凭值或名字编出中文枚举。

记录四个字典值可以说“当前字典返回的选项”，不能说“业务永远只有四种状态”。同样，不以字段只出现一个值推断固定默认值或必填约束。

## 7. 优化结构与实施顺序

### 7.1 沿用已拆好的模块，不再把业务规则塞回执行器

| 落点 | 负责内容 | 职责边界 |
|---|---|---|
| curate/evidence | 字段位置、原始类型、值、同条记录、页面/顺序等归一化输入 | 有上限的证据提取，来源仍可定位 |
| curate/rules | 信封角色、直接 value/name 配对、配置标签、实体 ID、参数传递、多字段对应等独立规则 | 输出事实或候选及作用域；不做 SQL，不用模型把猜测变成证据 |
| curate/planning | 新证据影响哪些名称/说明/字段/目录；整理规则和模型版本；复用与保护人工结果 | 基于输入变化更新，避免全量反复生成 |
| curate/interpretation | 中文名称、简短用途、详情解释、未知项、目录建议 | 输入按请求/响应和主要对象组织，保留推测的身份 |
| knowledge | 保存中文显示名、含义、来源、适用范围、关系类型、修改历史 | 明确 DTO 与迁移，继续通过同一事务和轮次回滚 |
| runtime/curation | 读公开端口、并发、进度、失败与写入 | 执行计划与命令，不决定字段含义 |
| 前端/MCP | 同一份知识的两种读取方式 | 显示中文名与原始键、摘要和展开依据；查询过程不现场生成说明 |

关系必须同时有源/目标 FieldRef（endpoint、请求/响应位置、状态、path）、匹配依据、环境、样本、可用的页面/操作顺序和确认状态。确认状态可用“直接来源”“观测对应”“语义推测/候选”；不引入难以校准的概率分数。

仅同值不是同一业务含义；已观测到数据传递不是完整调用依赖；字典选项不是所有消费者的完整枚举；人工确认和采样事实也不能混为一层。

### 7.2 分批做，每批独立验收

以下为调查阶段的初始实施先后。用户随后明确 MCP 场景导航的核心地位，后续以 [场景导航优先的实施方案](../architecture/0008-scenario-navigation-plan.md) 为准；本报告的调查证据与边界继续保留。

1. **锁定验收样本与证据表示。** 将本次明确错例、有效关系和禁止推测的例子做成脱敏回归样本。明确别名、单位、映射、关系的来源与范围，先支持本次证据类型，不建复杂通用规则平台。
2. **两层目录单独完成。** 统一深度约束、层级输出、旧目录差异和前端递归展示。它不依赖字段含义全部升级，可先获得直观效果。
3. **补解释输入与直接线索。** 字段位置、父级/兄弟字段、真实类型和值、页面场景进入解释；提取直接名称/值配对和当前列标签。修复咨询子单号、响应码、报价编码等错例，并区分接口名称与详细用途。
4. **按关系类型增量增加规则。** 优先做已验证的任务/验证码参数传递、列表详情、配置/商品多字段对应。过滤通用噪声，允许没有关系的接口保持空。
5. **统一成长判断。** 目前名称/用途只在缺失或有新结构时更新，字段通过输入摘要更新，目录总是重算且不把旧树交给模型。应使用统一证据版本、依赖和变更判断，使旧名称/用途/字段/目录都能受新证据影响，保留人工修改及历史。

规则阶段扫描可用原始证据，模型阶段只接收筛选后的摘要。保留当前限额的目的，但避免先截断关键选项再做匹配。更新可解释为什么某条说明被复用或重算。

本轮拟优化范围是整理。相同结构的新值持续保留属于后续采集/观测工作；任务持久化和 MCP 工具上线也各自实施，避免把一次知识质量改进扩大成平台重写。

### 7.3 验收题

- 再次整理之后目录仍有第二层，父目录在前端不会因自身无接口而消失；没有第三层或重复归属。
- 人能从名称区分管理端和供销云端的处理接口，知道详情聚合了什么、路径 ID 指向什么。
- itemCode 显示咨询子单号；estimatedAmount 在对应页面有“万”的单位，其他金额不继承该单位。
- 响应信封 code 不被写成物料编码；缩写不无依据展开成设计部。
- 模板的操作/意见/附件要求有直接来源，后台必填验证未证实就保持未知。
- 原始 20 项配置中的第 20 项能参与规则匹配，发给模型的上下文仍受控。
- 值传递和实体对应能显示源字段、目标字段及匹配依据；msg/size/sort 相同不构成业务关系。
- 咨询状态和未知类型码没有伪造枚举；无依据的接口关系保持空。
- 新线索能更新受影响旧知识，未变化记录复用；人工内容和回滚仍有效。

## 8. 小前端改动：对象数组元素不单独占行
