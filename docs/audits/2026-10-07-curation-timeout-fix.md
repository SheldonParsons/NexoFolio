## 原因及观察

后台已收到原任务 `8b560607-d6fc-4252-ba47-8361e0227207`，不是按钮完全未到达。实际项目有47个接口、60个样本、1738个字段，抽出的标量观测为85848条；之前用于语义验收的脱敏投影只有4338条，不能代替实际规模性能验证。

原任务从开始到打开接口说明轮次用了254.191秒。数据准备存在数组中逐项去重、每个接口重复计算全项目关系、字段规则反复扫全量信号；这些同步 CPU 工作直接运行在处理异步请求的线程中。观察到后台占用约100% CPU，健康接口3秒也超时。前端默认15秒超时，列表/进度读取或启动响应超时后统一显示“请求超时”并退出任务跟踪。

截图没有网络请求明细，不能断言红字具体来自POST还是之后的GET。运行日志明确证明后台已启动、准备阶段异常缓慢，前端任务跟踪会把传输失败当作整个操作失败。

最初核对时没有新说明；后续旧任务在中止前已保存2条接口说明。本次没有清掉它们，关闭了进程退出后遗留的 running 轮次并标为 failed，重试复用这2条说明，只补剩余45条。

## 修复

- 标量观测去重改为哈希集合，保留原行、值、位置、顺序与来源，不删样本、不缩小观测范围。
- 建立 SignalIndex，用接口、字段位置/路径、值、名称及同条记录查找；关系规则使用索引，仍保留原来环境、页面、顺序及确认条件。
- ProjectEvidence 只建立一次项目关系图，为所有接口投影字段输入；父级/兄弟字段分组一次计算。整个工作流共用同一个准备快照，不在接口和字段阶段重复扫全项目。
- runtime 专属 preparation 模块用 spawn_blocking 执行耗时分析；样本提取也移出请求线程。规则仍保持纯逻辑，数据读取、模型调用及知识事务仍在各自模块。
- 前端区分网络读取失败和后台任务失败。启动超时先GET确认是否已有任务，进度GET可有限重连；列表刷新超时不终止后台任务跟踪，完成后页面刷新失败也不会谎称生成失败。不自动重放POST。

本次不通过单纯加长超时隐藏阻塞，也没有更换模型或降低证据、关联判断质量。
