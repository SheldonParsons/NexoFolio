# 阶段4首轮：真实模型审阅与执行预算

日期：2026-09-16。阶段4测试已开始，**尚未通过阶段出口，未生成统一候选**。本轮只修改实验入口，没有修改生产重构逻辑、部署、发布、提交或推送。

## 1. 结论

当前执行器在这份真实数据上无法按生产预算完成全量审阅。模型连接和单片段合同可用，但输入组织、汇总方式与预算之间存在实际矛盾。应该先收敛阶段4执行器，再进行完整候选试验，不能提高上限后长时间盲跑。

这不是要求回头重新录制或改阶段1–3：资料已经进入固定快照；本轮发现的是如何把资料交给模型的问题。

## 2. 数据、配置与隔离

- 使用 `backups/recording-followup-20260916-passive/`，388条采集记录，其中153条HTTP观测、39个接口。
- 在一次性PostgreSQL恢复备份，迁移后用当前机械处理器重建派生证据；不注入虚构用户操作，不采用待裁决结构。
- 固定快照包含2,536个字段条目、5,817条事实，序列化为8,136,363字节。字段范围包含正式与未采用观测资料，不等于2,536个独立业务参数。
- 从当前worker读取的配置：`deepseek-v4-pro`、上下文配置65,536 tokens、最多256次调用、视觉关闭。上下文配置不是本轮测得的供应商容量。
- 生产算法将输入按字节保守限制为39,321，再将审阅片段限制为19,660字节；全局汇总每组只有6,830字节。字节与token不能混称。
- 两份固定备份的文件哈希均通过复核。主库仍为2个项目、39个接口、400条采集记录、0个维护任务、0条模型调用记录；主服务仍运行 `stage3-20260916` 镜像。

真实探针直接使用模型适配器，记录保存在本地实验目录，没有写入主库模型调用表。因此“主库0次”不等于本轮没有调用供应商。

## 3. 可复现的阻断

### S4-1：仅审阅就超过整轮上限

实际 `review_segments` 返回422段，至少需要422次审阅加1次规划，已超过256次上限。生产预检会以 `MODEL_BUDGET_INSUFFICIENT_FOR_REVIEW` 拒绝；这项保护是正确的，不能为了得到候选绕过它。

阶段3报告的128段使用64KiB测试片段预算，验证的是覆盖能力；生产片段预算为19,660字节。本轮使用生产预算，两者不是相同配置下的性能结果。

### S4-2：现有汇总再次逐批处理全部事实

`maintenance_engine/execution.rs` 将每条事实的 `data` 放入全局汇总，再加入全部审阅结果。仅事实项已有3,515,014字节；以6,830字节一组计算，第一层至少需要515组。该下界尚未计入接口、目录、审阅结果、分片开销、后续汇总层和回读，**不是已经执行了515次调用**。

现有预检只计算“未审阅片段＋一次规划”，没有涵盖这些必需开销。即使审阅勉强放得下，也可能花完审阅费用后才耗尽预算。

### S4-3：重复内容可以合并，但只合并祖先仍不够

离线实验把单元重复携带的祖先结构提到片段共享表，使用原有稳定ID引用，再逐单元展开，与原JSON完全相等。

| 测量 | 原输入 | 实验输入 |
| --- | ---: | ---: |
| 片段数 | 422 | 334 |
| 单元数 | 2,565 | 2,565 |
| 序列化字节 | 7,271,820 | 6,092,732 |

实验约减少16.2%的序列化字节，仍无法满足预算。字节统计的外层容器略有不同，用于工程比较；没有据此承诺token降幅。实验未接入生产，未将共享引用形式交给模型验证，不能把机械无损等同于模型阅读效果相同。

## 4. 一次真实模型调用

完整任务被预检阻断后，另外选择包含状态字段证据的 `segment-260`，只验证一个完整片段。采用当前生产模型适配器、系统提示及响应Schema，用户提示明确声明这是单片段探针，**不是完整任务的原样回放**。

| 项目 | 结果 |
| --- | --- |
| 实际供应商请求 | 1次，不重试；120秒超时限制 |
| 请求JSON大小 | 24,308字节 |
| 耗时 | 95.74秒 |
| 输入tokens | 7,730 |
| 输出tokens | 6,459，其中供应商报告推理tokens 5,169 |
| 总tokens | 14,189 |
| 审阅覆盖 | 7/7单元，无重复遗漏 |
| 引用存在性 | 全部能在固定快照解析 |
| 候选/发布 | 均未发生 |

以上用量来自供应商 `usage`。不把一次样本线性外推为整轮时间/费用，也不以此推算模型容量。

人工检查发现：模型把只见过null的字段保留为需要更多证据；状态值仅作为不完整候选，没有宣布完整枚举；ID没有被当成枚举。但部分“change”只是备注/类别等字段名解释，未证明带来业务信息增益。输出把 `{type:"null"}` 简称为“schema为null”，措辞不够准确，后续需区分明确观察到JSON null与完全未观察到结构。

覆盖与引用有效只证明输出结构合规，不证明证据足以支持结论。没有测试全局策略、跨接口关系改善或完整文档收益。

本地保留完整准备请求，以及解析后的模型输出和usage；不宣称保存了供应商完整HTTP响应封装。第一次探针启动因Docker挂载的 `/host_mnt` 路径在宿主机不可读而在读取密钥前退出，未发请求；修正本地路径映射后才执行上述唯一供应商调用。

## 6. 下一步优化方案

先在阶段4内部完成以下收敛，再试一次完整运行，不新增业务服务或另一套流水线。

| 位置 | 为什么改 | 具体改法与验收 |
| --- | --- | --- |
| `crates/rebuild/src/maintenance/review.rs` 及相关上下文装配 | 修复重复上下文挤占审阅预算；单独祖先去重已证明不足 | 按接口/环境共享身份和上下文，字段保留唯一ID、原结构和证据引用；检查其他重复部分后统一打包。保留原文展开与全字段覆盖测试，不能静默删除未采用字段或抽样。小范围验证模型理解后再完整运行 |
| `crates/application/src/maintenance_engine/execution.rs` 与 `maintenance_engine.rs` 的 `global` | 收敛二次全量事实汇总，避免普通keep结论被反复交给模型压缩 | 用完整机械索引保存事实及所有审阅记录；规划输入集中呈现目录、全接口索引、发现/冲突和跨片关系；原件仍按稳定引用回读。发现过大时才做分层汇总，不能以索引替代全字段审阅 |
| 同一执行器的预算预检和请求装配 | 修复当前预检低估调用数，减少多层固定预留造成的空间浪费 | 按实际准备请求计入Schema/提示/索引开销；预算覆盖审阅、必需汇总、规划和有界回读/重试。明确保留输出空间；token估算不可靠时仍需保守保护，不直接把字节上限乘常数。无法完成时在首个付费调用前给出明细 |
| 现有模型提示与候选审查测试 | 修复“有修改”被误当“有收益”的验收缺口 | 用本轮字段名复述、null措辞作回归样例；普通ID/协议字段可keep，有证据的业务描述才提修改。只调整实际复现的问题，不同时堆叠多套prompt |

出口标准：同一固定快照全部字段覆盖；每个修改目标和支持资料可回读；一轮实际调用在预先说明的预算内结束；生成有效候选，并人工检查相对现状的收益。如果预算仍不够，报告测量结果后再决定，不能暗中提高上限。

完成上述修复后，阶段4继续真实完整候选测试；通过后进入阶段5文档拼装，再到阶段6隔离发布/回退。当前无需用户补录数据。
