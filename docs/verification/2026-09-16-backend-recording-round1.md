# 真实样本后端检查：第一轮

使用修复后补充快照 `9ab07494-76ba-4ca6-b2c2-c90d23ebc774` 的隔离副本，保留原179条基线。没有修改生产业务逻辑、没有写主库、没有调用模型，也没有向真实平台重放HTTP请求。

## 方法和覆盖

- 在一次性PostgreSQL恢复快照，READ ONLY查询原始观测、当前定义、差异和证据。
- 用实际Rust `extract_observed`、`definition_covers`、`eligible_relation`、`parameter_link_fact`、`unambiguous_ui_targets`重新执行固定样例。薄执行入口为`apps/backend/examples/recording_regression.rs`，私有JSON通过stdin传入；输出不含原始正文。
- 选取3类真实差异，执行13项可复现检查；其中“将已有元素数组变空、再加无关字段”为明确标记的派生样例，不冒称新录制。
- 检查10条真实参数关系候选的资格与推断性质，以及12份新增UI快照的unknown排除规则。此项没有把候选当作正确关系来计准确率。
- 检查快照内8条待确认差异与当前修订的引用关系及发布状态。

结果记录位于本地忽略目录`experiments/results/backend-recording-round1/regression.json`。所有13项结构检查通过；10条关系仍保持inferred，12份快照均未将unknown控件作为已知值。

## 具体结果

| 样例 | 运行结果 | 结论 |
| --- | --- | --- |
| userMenu抽取超限 | 初始/拟议定义均可从原文重现。原文仍有msg/popupType，预算化结构没有；明确带STRUCTURE_EXTRACTION_LIMIT，未被当成重复证据 | 确认缺项来自抽取预算，不能称字段被业务删除 |
| getProjectInfoByParam | null→number/string可重现；当前covers=false | 当前统一进入待确认，尚未区分“信息补全”与更强的结构差异 |
| 商品列表records | 空→有元素为新信息；以实际有元素响应派生空数组后，covers=true；再加无关新字段，covers=false | 不因空数组丢失已有元素结构，也不忽略其他真实新增字段 |
| sort→size、图片尺寸→轨迹坐标等候选 | 当前候选资格过滤仍允许进入，但仍是inferred/complete=false，即使搜索唯一且无交互支持也不成为confirmed | 去噪/可信度排序还有改进空间，不能把ambiguous=false理解为业务关系正确 |
| UI unknown | 所有eligible控件均排除了unknown | 不应靠猜测下拉底层ID来制造映射 |

## 当前数据是否被错误覆盖

隔离快照中8条差异均为pending，8条都仍指向当前基线修订；目录版本、知识发布版本均为0，没有已发布知识。没有发现参数关系候选被存成确定结论。

因此，本轮发现的是解释和候选质量待完善，不能笼统说系统已把这些差异确认为接口变更。也不能因保护检查通过就声称整个知识维护已经验收。

## 接下来应处理的事项

1. 差异应能区分重复、信息补全、实际结构差异、抽取不足，并保留证据；本轮不自动裁决或改变当前定义。
2. 参数关系降低仅由相同数值产生的噪声，尤其排序号、分页大小、坐标等；日常A/B交错使用下不能由邻近时序推断业务意图。
3. 保持unknown、部分字典、文件元信息投影、跨视图与异步请求的能力边界，再进入LLM知识候选质量验证。

这是一轮限定范围的真实数据检查，不包含完整发布/回退、并发压力或真实模型生成验收。现有数据足够继续定位这些后端问题，暂不要求用户重新操作插件。
