## 目标与约束

- 知识集中存放在服务端，经 HTTP MCP 提供给不同 agent。
- 文件系统是虚拟导航与操作语义，不依赖个人本地文件或挂载。
- 新接口入库后立即可查，优先尝试现有分类，无法确定时进入待分类视图。
- 目录组织可替换；正式接口、目录视图、搜索索引分别管理。
- 冲突形成待裁决变更，不覆盖已确认定义。
- 普通用户由禅道验证；超级密码允许登录任意已有用户，不创建身份或提升权限。登录及项目读取准入已实现；登录时同步可见范围，日常只查本地授权，动作权限和裁决暂不实现。
- MCP 使用独立管理入口签发的专用 Bearer Token，绑定已同步项目和读写权限，按有效期与撤销状态校验。
- 内部登录 Token：普通登录先通过禅道鉴权，再复用未过期的有效 Token；没有或过期才签发新的 3 个月 Token。复用不改变值或到期时间。后续业务只查内部 Token 与本地授权，不访问禅道。
- 项目只从禅道同步，平台不提供创建项目入口。
- 已登录用户在平台列表可看到已同步项目的基础信息和可访问状态；项目内容与操作仍由后端按禅道权限逐请求控制。MCP 继续受专用 Token 项目范围限制。
- 普通禅道登录成功后增量同步用户可见项目：读取全部状态，仅新建 doing 项目；已有项目不重复创建，仅维护外部状态等同步元数据，不删除知识。同步不要求预先提供超级账号，覆盖范围随用户登录逐步积累。
- 每次普通禅道登录成功后同步一次项目和用户可见范围，复用未过期内部 Token 时也同步。以后增加独立同步接口，允许已登录用户主动同步而不重新执行平台登录、不更新内部 Token；两个入口共用同步服务。普通请求鉴权不触发同步，裁决授权暂不确定。
- Chrome 插件走独立的高频批量 HTTP 接收入口，重复观测尽早结束；模型、触发评估和重构在后台处理。
- 使用 Cargo workspace 把 intake、triggers、rebuild 等能力隔离为独立业务包，并检查依赖方向。
- 为后续跨项目迁移和选中导出保留系统级接口 ID、可变项目归属、显式依赖和版本化导出数据模型；功能后续实施。
- 第一阶段验证固定目录、数量触发整理、问题驱动局部整理的实际效果。

按独立部署的实验服务选型；生产规模、可用性目标和部署平台尚未确定。

## 建议技术栈

| 层次 | 选择 | 原因及边界 |
| --- | --- | --- |
| 后端语言 | Rust stable + Tokio | 用类型表达状态、版本和错误；初始化时锁定工具链并验证依赖组合 |
| HTTP 应用 | Axum + Tower | 提供导入、管理、任务状态接口；MCP 由 SDK 提供协议处理 |
| MCP | 官方 Rust SDK：rmcp | Streamable HTTP；接入层保持薄，不把知识业务写进工具处理函数 |
| 数据契约 | Serde + Schemars + 显式业务校验 | Serde 负责序列化，Schemars 描述 JSON Schema；业务约束和模型输出有效性仍需单独验证 |
| 主数据库 | PostgreSQL 17 + JSONB | 用关系约束管理身份、修订、目录、事件；JSONB 保存灵活的接口结构 |
| 数据访问与迁移 | SQLx + SQL migrations | 显式 SQL 和事务便于实现修订、增量与原子发布；迁移和回填需单独设计 |
| 检索 | 精确字段与词面匹配起步；pg_trgm、pgvector 作为实验组件 | 先验证 ID、路径、名称、别名搜索；语义检索按对照实验决定是否启用 |
| 后台任务 | Rust worker；优先验证 Apalis + PostgreSQL | 归类、摘要、候选生成、评估在 worker 执行；框架恢复和重试行为须通过实验后定版 |
| 模型调用 | 小型模型适配层 + 提供商 HTTP API/SDK | 分开定义生成和 embedding 能力，模型、提示词、参数可配置并记录版本 |
| 实验与验证 | cargo test + 固定数据集 + MCP 回放程序 | 系统一致性测试和真实 agent 召回评估分开 |
| 依赖管理 | Cargo.lock + rust-toolchain.toml | 锁定服务依赖和具体工具链版本，复现实验环境 |
| 部署 | Docker Compose | 初期按 api、worker、PostgreSQL 设计；后台任务框架验证后确定最终依赖 |

以上主版本是建议基线，不代表整套组合已运行通过；部署镜像也需固定版本或摘要。

## 核心选择理由

### Rust 与 Web 框架

用户倾向 Rust，本轮将其作为后端首选候选。当前主要工作是远程模型调用、目录与版本管理、数据库读写，适合先验证 Rust 服务实现。
类型系统可帮助检查状态分支和模块接口，但不能自动保证目录质量、数据库一致性或任务恰好执行一次。
Rust 的工具链与类型处理会增加初期开发成本；本项目整体延迟很可能主要受模型调用和数据库影响，需要实际测量，不能预先声称切换语言会显著加速召回。

Axum 和 MCP 是两种入口，调用同一组应用服务；避免内部通过 HTTP 互调自己来复用逻辑。
官方 rmcp 的 Streamable HTTP 服务可通过 Tower 服务挂载到 Axum。需要验证生命周期、超时、鉴权上下文传递及真实 HTTP 客户端调用。
当前仓库主分支文档不等于已发布 crate 的全部能力，初始化时应选择已发布版本并验证版本组合，不能直接依赖 main。

稳定的身份、修订和发布状态使用明确的 struct/enum；开放的接口结构使用受校验的 JSON 数据。
阈值、提示词和实验参数保存在配置中并记录版本，调整实验参数不应要求修改业务类型。
根据用户对探索期模块隔离的要求，改用 Cargo workspace 和独立业务包；只为确实需要替换的模型、组织策略、检索和存储边界设计 trait。

### PostgreSQL 是正式数据来源

正式记录、不可变修订、证据来源、变更提案、目录版本、目录成员关系、构建任务、增量事件保存于 PostgreSQL。
接口内部结构可用 JSONB；身份、权限范围、版本、关联关系等需要约束和查询的字段单独建列。
原始导入件如需逐字保留，应保存原文或原始字节；JSONB 不保留原始格式。

数据库内容通过 MCP 渲染为目录摘要、Markdown、JSON 或 YAML。
“文件路径”是导航地址，写入使用稳定 ID 与基础修订版本，权限绑定项目和记录身份。

### Worker 负责执行，数据库负责恢复

优先验证 Apalis 的 PostgreSQL 后端。需要单独验证任务领取、失败重试、进程强退后的回收和长任务重复执行行为。
业务写入和待派发事件在同一事务提交。如果框架不能直接复用业务事务，则用数据库 outbox 派发任务，允许重复投递。
worker 根据任务 ID、输入修订、执行归属和检查点实现幂等；失去执行归属的旧 worker 不得发布结果。
不能把 Tokio spawn 或任务框架本身当成持久恢复与恰好执行一次的保证。任务状态和检查点保存在 PostgreSQL。
目录发布用事务比较当前版本后切换，后台构建不占用长数据库事务。

构建快照必须对应明确的数据边界。普通自增序号不等于提交顺序，不能仅以 MAX(id) 判断增量已经补齐。
实验阶段可采用项目级事务内递增事件序号，并以一致快照读取内容和边界；发布后继续合并未覆盖事件。

### 检索先建立基线

目录导航、精确查找和词面搜索属于首轮能力。向量检索是待验证的候选召回方式，不决定正式数据模型。
中文业务词、短字段、URL 和混合中英文名称需要独立测试。pg_trgm 是字符相似度能力，不能等同于中文分词或业务语义理解。
需要分词时，在独立检索适配器中实现，不能声称默认数据库全文检索已经解决中文召回。

启用 pgvector 后先使用小规模精确向量搜索作为参考，再评估近似索引。
项目过滤可能影响近似搜索的返回数量和召回，应专门验证。embedding 保存模型、维度和输入内容版本，换模型时重建索引。

## 为重构保留的模块边界

建议按独立业务包组织代码：access、knowledge、intake、triggers、rebuild，由 application 编排。
contracts 保留少量跨边界类型，infrastructure 实现外部能力，apps/backend 装配 HTTP、MCP、worker 和 CLI。
核心业务包相互不直接依赖，依赖白名单由 CI 检查；详细目录和各包所有权以模块化架构文档为准。

目录组织拆成四个独立步骤：

1. TriggerPolicy：输出检查范围、触发原因及相关指标。
2. CatalogBuilder：输入确定快照和约束，输出候选目录。
3. CatalogEvaluator：比较候选、现有目录及最小修补方案。
4. CatalogPublisher：验证版本条件，原子发布并保留回退依据。

策略、模型与提示词版本写入每次实验记录。目录成员关系使用稳定接口 ID，重分类不迁移接口正文。
初期采用节点表、父节点关系和成员表；无须先引入图数据库或完整工作流平台。

## 首轮实验与通过条件

### 技术链路

- 通过真实 HTTP MCP 完成列目录、读取、搜索、提交变更和查询变更状态。
- 所有工具使用一致的项目范围、身份校验、版本字段和分页/截断语义。
- 首个真实 agent 客户端完成端到端调用；其他客户端随后执行同一契约用例。
- worker 重启或重复投递后，任务可恢复且不会重复发布。
- 构建期间持续新增、修改、删除，发布后无漏记录、错误复活或断引用。
- 基于旧修订提交的冲突进入待裁决，正式定义不被覆盖。

### 目录效果

同一初始数据集、同一增量事件流、同一查询集，比较：

1. 固定目录 + 增量归类。
2. 数量触发整理。
3. 根据归类困难及查找问题做局部调整。

评估正确接口与证据的覆盖、归类纠正率、工具调用数、读取 token、耗时、目录变动范围和模型成本。
分别记录 agent 型号与版本；用于调参和最终验证的问题分开，包含冷门、跨分类、新接口和无答案问题。
HTTP 200、工具调用成功以及模型自报置信度都不能替代召回验收。

## 后续扩展的条件

- 数据库检索经调优仍不能满足实测召回或延迟要求：再评估独立搜索/向量服务。
- 原始样例体积或保留周期使数据库不适合承载：增加服务端对象存储，保留元数据与哈希引用。
- 构建任务出现复杂跨步骤恢复需求：再评估专门的工作流编排系统。
- 多机容量或高可用需求明确：再扩展应用与 worker 部署。
- 模型选择单独基于中文业务归类、结构化输出和成本实验决定，本次不指定供应商或购买算力。
