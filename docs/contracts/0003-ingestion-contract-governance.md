# 多类型采集与契约对齐机制

状态：机制设计与后续路线；2026-09-14。后端已实现首轮机器契约、批量接收、环境与结构去重、可靠下游入口；图片/页面元素及下游处理尚未实现。当前实际协议以 0004-ingestion-and-environments.md 和 contracts/ingestion 机器契约为准。

## 1. 根据现有代码发现的问题

后端 crates/intake/src/models.rs 的 CaptureInput 目前包含 method/url、无约束 request/response JSON 和单一 source_complete。
插件 src/capture/contracts.ts 已有请求/响应正文与头的独立状态、编码、字节数、截断 URL、XHR/Fetch 和 frame 信息。
上传适配器不能把这些状态压成一个布尔值，也不能把未采到的正文变成空 JSON。
插件行 ID 为进程内递增数字，不能作为跨重启上传幂等 ID。
用户明确：20 条是测试阶段界面限制；所有授权采集记录都要进入独立持久上传队列，未确认记录不因数量溢出而淘汰。后续界面策略与上传生命周期分开。
用户明确：上传内容不做脱敏，不自动替换或删除 Authorization、Cookie、业务字段及正文值。指纹使用的值抽象仅为判重计算，不改写采集原文。调研时已脱敏的历史证据不据此还原；测试默认使用合成样例，真实采集正文不写入公共源码或日常诊断日志。

## 2. 通用传输层与类型处理器

采用“批次信封 → 条目信封 → 特定类型 payload”的形式。一批只属于一个明确项目，同一次发送可包含多个受支持类型。
信封承担协议版本、批次 ID、条目 ID、项目、来源、采集时间和类型；不要求所有类型都有 method 或 HTTP response。
具体 payload 按 kind + payload_version 选择 Schema 和处理器。

首轮只实现 http_exchange；image、page_element 是后续类型设计方向，当前不宣告支持或接受后丢弃。
图片等大内容后续通过受权限控制的附件上传与 artifact_id 引用接入，不把任意大 base64 内容塞进 HTTP 采集正文。
附件权限、完整上传、过期清理和引用校验在实现该类型时定义，不预先暴露空壳接口。

模块职责：

- 通用 intake：批次解析、身份和项目授权入口、大小/速率限制、版本检查、逐条回执、可靠接收。
- intake/http_exchange：HTTP 身份规范化、正文状态、结构指纹、已知变体判定。
- 未来的 image/page_element 处理器：实现各自的校验与信息提取，不修改 HTTP 指纹逻辑。
- application：编排可靠接收、数据库事务和后续任务；triggers/rebuild 继续消费语义事件，不理解各种原始上传正文。

采用显式注册的处理器与能力清单；当前不需要动态装载插件或通用执行任意脚本的机制。
跨模块只暴露稳定类型和 ports，插件内部 UI 对象先经过上传转换器，后端传输 DTO 再转换为业务模型。

## 3. 权威来源

建议在后端仓库新增顶层 contracts/ingestion/，保存跨仓库传输契约。
它与 crates/contracts/ 的职责不同：前者是对外可分发的机器契约；后者是 Rust 内部共享类型。

```text
contracts/ingestion/
  manifest.json              # 版本、契约摘要、支持类型
  batch.schema.json          # 通用批次/条目信封
  receipt.schema.json        # 回执和错误
  http-exchange.schema.json  # HTTP payload
  behavior.md                # 字段语义、幂等、失败和重试规则
  fixtures/                  # 正常与异常、期望结果
```

JSON Schema 是传输结构的权威来源，不分别让 TypeScript interface 和 Rust struct 自称权威。
TypeScript 类型与校验器由权威契约产生；Rust DTO 可采用经过验证的生成工具或显式映射，但必须用同一套正反例验证实际反序列化、序列化和约束。
不简单对比两个 JSON Schema 文本是否相同：文本不同可能语义等价，Schema 相同也不能证明状态、事务和重试语义相同。
行为用例补足结构 Schema 无法表达的规则，适配器无权自行更改“缺失”“空值”“截断”“成功”等含义。

## 4. 修改合同如何被发现

### 同一 Rust workspace

- 保留已实现的依赖白名单检查与关键禁止边测试。
- 模块公共类型变更必须通过 workspace 编译和各消费者测试。
- 触发、重构、知识发布等独立验证行为契约，不能把编译通过当作运行语义兼容。

### 插件和后端不同仓库

- 分发一个版本固定、可核验摘要的契约包，插件锁定具体版本；不在运行时追踪 main 或 latest。
- 可先用版本化打包产物/固定提交引入，后续需要时再建立专用仓库或包发布服务；无需现在新建第三个业务仓库。
- 插件 CI 检查生成文件是否落后，并使用真实上传转换器生成 payload，用同一 Schema 验证。
- 后端 CI 将插件输出的合成契约样例送进真实接收路由，验证回执、去重和错误处理。
- 后端生成的回执进入插件消费测试，验证接受、拒绝、逐条重试与登录失效处理。
- 契约变更检查要求版本/变更说明同步更新，并运行当前版及保留旧版的兼容用例。
- CI 状态应配置为分支合并要求；有检查脚本但不运行或允许直接绕过，不能声称能阻止错误发布。仓库保护设置在启用该机制时另行配置。

单次对话或发消息给另一任务用于通知，不能充当契约一致性的唯一机制。
本轮只是建议，不声称以上跨仓库生成与 CI 已部署。

## 5. 版本和发布

通用信封版本、各类型 payload 版本、应用软件版本、结构指纹算法版本分别记录。
HTTP 指纹算法升级不必改变传输契约；增加图片类型也不必改变 HTTP payload 的解释方式。

删除/改名字段、改类型、改变空值/缺失含义、改变成功或重试语义均需要显式兼容方案，通常升级主版本。
新增可选字段也不能无条件判定兼容：旧消费者若拒绝未知字段，仍可能破坏兼容。新增 enum 值同样需要旧客户端测试。
运行时建议提供采集能力查询，声明支持的信封/类型版本及批次限制；插件只发送双方共同支持的版本，不强迫旧插件同时升级。
服务端不支持某条类型/版本时明确逐条拒绝；支持的其他条目继续处理。无法识别整个信封或未通过整批授权时拒绝整个批次。
发布顺序：后端先支持新旧契约 → 插件按能力协商使用新版 → 验证旧客户端覆盖 → 再单独安排旧版下线。
回退插件不得要求清空全部数据；队列条目保留所用契约版本，不能在重试时悄悄按新语义重新解释。

## 6. 批量上传必须明确的语义

- 一批一个项目；绑定变化不修改已排队条目的原始项目归属。切换账号/服务后暂停旧队列，不能用新用户凭证上传旧用户数据。
- 条目在首次入队时分配跨重启唯一 ID。相同条目重试保持 ID、版本、项目和 payload 不变；同 ID 不同正文返回冲突，不静默覆盖。
- 界面数据与上传队列分开，队列持久化、容量和采集背压需明确实现。不得淘汰未确认记录；本地容量耗尽时暂停新增采集并明确提示，已有记录保留并继续上传，不能承诺无限存储。
- 请求未完成时先等到可提交状态，首轮优先提交完成/失败/超时等终态快照；晚到的补充若要支持，必须定义独立更新协议，不能修改已发送幂等条目。
- 条数、编码后字节数、最长等待时间任一达到条件即发送；单条和整批均有限额，限制来自服务能力及客户端配置。
- 分开观测 HTTP 接收耗时和后台处理完成时间。accepted 只表示已可靠接收，不表示已生成正式接口文档。
- 批次部分成功时按条目回执出队；临时失败沿用条目 ID 退避重试，永久拒绝保留原因。丢失整批响应时原条目可安全重发。
- 401 暂停上传并恢复登录；403 处理项目权限，不清空用户 Token；限流遵循退避，服务端不得接收后无声丢弃。
- 相同原始观测与相同接口结构是两层去重，不能因为 payload 哈希不同就认定接口定义变化。

数值限制需结合插件当前每个正文最高 1 MiB、编码膨胀和请求/响应合计大小制定，不能给出小于正常单条的批次上限后强行截断。
首轮通过合成或授权的真实流量回放确定初始上限与等待时间，再作为可配置实验参数；本文件不宣称已有最优值。

## 7. 建议的落地顺序

1. 整理插件真实采集字段，制作完整响应、空正文、网络失败、截断、重复头、重试等契约样例。
2. 写批次、HTTP payload 和回执 Schema，并配套状态/幂等/错误行为表；其他类型仅保留扩展边界。
3. 先实现双端契约校验和兼容反例测试：故意改字段名/类型/状态语义，应在发布前检测到失败。
4. 再实现插件独立上传队列与服务端批量接收，保持当前已验证的登录/绑定行为。
5. 完成断网、重启、部分失败和新旧版本对照后，再进行高频去重优化。

验收应至少证明：改动契约能定位受影响消费者；已知重复不重复入库；未知类型不伪报成功；截断不变成空响应；第 21 条界面记录淘汰不会丢待上传内容；服务端升级不要求所有插件同时升级。


## 8. 一批 HTTP 观测的明确处理流程

以下为当前建议的处理顺序，上传实现尚未开始。全量上传沿用用户此前“后端可忽略已存在且无变化接口”的规则，不自动解释为服务器永久保存每一次重复调用。

1. 插件将所有授权观测持久入队，生成稳定条目 ID；同一用户/服务/项目组成批次。界面显示记录不承担可靠上传职责。
2. 后端验证内部 Token、本地项目权限、信封版本和批次大小；整批鉴权失败不处理条目，格式可解析但个别类型/正文无效时逐条拒绝。
3. 按条目 ID 和正文摘要识别重试：同 ID 同内容返回已有回执，同 ID 不同内容冲突；已持久接收但仍在处理的条目不重复入任务。
4. 对 HTTP 类型计算身份及观测结构，查已知变体。确定已处理且无新增信息的返回 ignored；不完整、无法判断或新变体均进入持久接收，不为了快而伪报无变化。
5. 对需要处理的条目，在短事务中保存待处理输入/引用及任务事件，提交后返回 accepted + ingestion_id。外部模型、归类和重构不阻塞这一轮回执。
6. 插件按条目回执出队；accepted/ignored 可结束上传，临时失败保留重试，永久拒绝保留可见失败记录。丢响应可沿用原 ID 重发。
7. 后台重新检查当前记录/修订和已知变体，处理并发期间已产生的相同信息：新接口建立 observed 记录；已有接口无新增信息结束；新增样例按策略记录；正式定义冲突建立或复用待裁决，不覆盖正式内容。
8. 新接口记录提交后即可按 ID 和基础搜索发现。分类器先匹配现有目录；明确匹配则建立引用，不确定则待分类。正式与候选目录各维护自身归属。
9. 只针对新接口、确认后的知识变化、归类困难等语义事件更新聚合指标，再交触发器判断。原始重复请求数量不直接触发目录全量重构。
10. 触发器可以输出不处理、局部检查或重构意图。重构器生成候选方案，评估后由独立发布服务切换目录；其过程不影响新批次接收。裁决操作规则尚未确定，本阶段不展开。

传输回执与后台结果是两层状态：accepted 只证明可靠接收，后续应能按 ingestion_id 查询处理完成或失败。具体状态查询端点与保留周期在接收契约落地时一并定义。

最新环境规则：项目内独立环境实体拥有UUID与中文显示名称，可列表选择或手填；上传按名称解析/创建，按ID比较，改名保留旧别名。协议版本与正式接口版本分开，采集不指定历史版本；当前环境状态变动的观测进入下游，不能因历史曾出现过就忽略。

用户最新范围约定：domain＋path确定插件采集范围，选择项目后加载环境列表并绑定一个环境。项目＋环境为去重分区，不再有service_key；外部上传使用v2，服务端兼容未修改的v1队列。以根机器契约和0004文档为准。
