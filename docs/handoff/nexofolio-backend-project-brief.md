# NexoFolio 后端项目介绍

本文供首次接手项目的开发 agent 使用，整理产品背景、用户要求和当前仓库事实，不指定新的实现方案。

代码状态核对基准：`main` 分支，提交 `d6c14f4`。后续开发前请重新核对实际代码与运行环境。

## 1. 这是一个什么产品

NexoFolio 希望成为一个面向人和 AI agent 的接口知识库。

用户希望把实际系统中的接口调用及相关资料收集起来，逐步形成容易查找、理解和维护的接口文档。除了请求方法、路径和字段结构，还希望获得接口用途、参数含义、可能的参数来源关系、枚举及业务标签等信息。

重要使用对象是 Codex 等各种 agent。用户希望 agent 能像浏览一个项目的文件目录一样理解接口知识，按需查找内容，并通过受控能力提出或执行修改。这里的“像文件系统”描述的是使用体验，不表示知识库必须落在某个人的本地目录，也不限定服务端必须采用真实文件存储。

知识库最终通过服务端 HTTP MCP 对外提供能力。前端用于人查看、管理和审核接口资料；Chrome 插件是目前主要的数据来源，以后还可能接入其他平台。

## 2. 当前为什么重新开发

项目已有一轮接收、去重、证据整理、目录生成和知识维护的实现，但用户认为代码和流程过于复杂、难以理解及修改，要求先删除相关实现，再逐个环节重新开发。

历史测试中，一轮包含39个接口的模型任务耗时约58分钟、调用165次，最终生成目录归属，没有新增参数描述、关系或枚举注释。这是旧实现的实际问题，不是新方案必须遵循的流程或性能目标。

用户明确表示不担心重做或删除旧代码。接手者不需要为复用旧设计而增加复杂度，也不需要恢复原来的审阅、分段、回读或证据机制。

旧实现可在提交 `f2d4ae3` 中查阅，主要用于了解历史行为、失败案例和已有数据；它不是新的设计规范。

## 3. 用户明确提出的工作方式

- 逐个环节讨论清楚，再实现、验证和反馈；不要一次铺开整套系统。
- 模块之间需要严格的代码隔离，边界应能验证，不能只有目录名称上的划分。
- 模块间合同需要明确、可核对。合同变更时必须识别受影响的调用方，避免一个模块改动导致其他模块无声失效。
- 关注代码是否必要、是否整洁、规模是否合理，不能只证明“功能能运行”。
- 验收应包含实际业务效果，不能把测试通过、模型返回成功、候选状态成功等同于文档已经有价值。
- 用户希望按阶段收到结果反馈，不使用自动持续推进的目标模式。
- 不使用 GitButler，不创建或使用任何 Git worktree；直接在当前项目目录和普通 Git 分支工作。
- 不调用、恢复或安装 ego lite 浏览器。
- 后端、前端、插件是独立项目。跨项目接口变化需要对齐，不能把接手后端自动理解为可以改动所有客户端。

## 4. 身份、项目与环境

以下业务规则已有明确讨论，其中登录、项目及环境基础能力保留在当前代码中。

### 用户登录

- 普通用户使用禅道账号验证身份，NexoFolio 保留本地基础用户信息。
- 普通登录仍需先通过禅道认证；随后签发或复用内部 Token。
- 内部 Token 有效期为3个月；已有 Token 未过期时继续使用原 Token，不因为重新登录而刷新有效期。
- 登录后的业务请求使用内部 Token，本地鉴权不逐请求访问禅道。
- 保留超级密码入口，可登录已有本地用户；不通过它创建用户，也不增加该用户的项目权限。

### 项目与权限

- 项目来源于禅道，不在本平台随意新建。
- 普通登录成功后同步一次该用户可见的项目。
- 本地不存在的项目，仅在禅道状态为进行中时创建。
- 已存在的项目不重复创建；状态发生变化时保留项目并记录状态，不删除。
- 项目列表可以展示当前用户无权进入的项目，但访问项目内容必须由后端拒绝，不能只靠前端提示。
- 用户希望以后可以不重新登录而主动同步项目；当前独立同步入口尚未实现。

### 环境

- 同一项目可能绑定多个域名或路径范围，域名不能直接等同于项目身份。
- 插件先选择站点范围（domain＋path），再绑定项目和环境；项目、环境是接口处理的重要归属范围。
- 插件需要能选择已有环境，也能填写名称；此前要求是名称不存在时可创建环境。
- NexoFolio 内部也需要管理环境名称，并提供项目环境列表。
- 环境名称修改不应让原有接口资料失去归属。

MCP 使用独立签发的专用 Token，不直接复用普通用户登录 Token。当前专用 Token 管理尚未完成。

## 5. 外部采集与接收需求

- 主要输入来自 Chrome 插件监听到的 XHR/fetch，频率可能很高。
- 用户大部分时间不会意识到自己在“录制”，可能在不同业务操作之间切换。不能默认连续操作就是一个完整业务场景，也不能仅凭同页或相邻时间认定因果关系。
- 大部分接口调用可能对应已有且未变化的结构，性能和重复数据规模是重要问题。
- 支持批量上传；上传方未来不限于插件，公共接口不应绑定插件内部实现。
- 后续输入可能扩展到页面元素等其他资料，不能把所有输入永久限定为一种HTTP记录。
- 用户明确要求原始采集不脱敏。
- 插件只显示20条记录是历史测试界面限制，不是只上传20条的业务规则。
- 截图采集已明确暂缓，不应作为当前重新开发的前置条件。

接收协议、数据格式、记录ID规则、接收成功的含义、同步/异步处理边界、保存期限和具体性能指标，均需要重新讨论。上一轮建议过的“先可靠接收、后台判断结构”并未得到用户最终确认。

## 6. 接口知识希望具备的能力

这些描述的是产品期望，不要求在一轮开发中全部完成。

- 识别接口及其项目、环境归属，避免同一个接口因请求数据不同而重复建档。
- 对路径参数有合理处理，例如不同ID值不应天然产生不同接口；具体模板识别规则可以重新设计。
- 区分字段结构与实际值，避免列表中每条数据都重复生成一套对象结构。
- 空数组、null、未采集完整等情况不能直接作为字段删除或结构变化已确认的依据。
- 结构相同的调用仍可能带来新的有用资料，不能直接推导为整条调用没有价值。
- 有冲突的接口变化可以作为待裁决保留；具体裁决机制尚未确定。
- 每个环境重点维护当前有效版本，历史版本用于查询和追溯；具体版本数据模型尚未重定。
- 文档最终应容易跨项目迁移，并支持导出选中的部分内容。这是后续需求，不要求现在就实现完整迁移/导出系统。

参数关系的例子：A接口返回一个ID，B接口请求中的record_id可能使用了这个ID。用户希望能够发现并说明这样的关系，但值相等、发生时间相近不等于已证明来源。

枚举资料有两类来源：接口直接返回字典/选项，以及前端控件在交互中选择某个值。观察过少量取值不意味着已经获得完整枚举；页面文字和传输值的对应关系也需要依据。

## 7. 目录与知识维护期望

- 知识库需要能持续整理目录，适应接口新增和变化。
- 用户此前希望正式目录包含一个固定、不可随意修改的“待分类”子目录，用来容纳尚未归类的接口。
- 目录整理不希望被固定为“数量达到阈值就全量重建”，希望能够考虑现有组织是否成熟、实际需要改变的范围。
- 用户希望 LLM 能参与目录组织及接口、参数说明的完善，并考虑全局信息。
- 对全局的理解不等于已经决定采用逐字段全量模型审阅。此前耗时很长的流程正是此次重新设计的对象。
- 用户关心知识能够在多次维护中升级、修正，并且修改有来源、可审核、可回退。
- 此前人工发布权限沿用项目访问权限，没有建立独立管理员角色体系；新流程中的发布合同和角色细节需在对应环节确认。

模型如何参与、输入如何组织、分析与生成是否分开、目录和语义是否同轮维护、怎样定义完成、是否需要候选，以及何时触发，均不由本文预设。

## 8. 当前仓库实际保留了什么

当前代码基于 Rust Cargo workspace，主要技术为 Tokio、Axum、Tower、Serde、SQLx/PostgreSQL、rmcp。工具链由rust-toolchain.toml固定，依赖由Cargo.lock锁定。以下是现状，不要求新业务照搬同样的目录布局。

```text
apps/backend/                     API、空闲worker、管理CLI及传输装配
crates/common/                    基本ID、错误、Secret、数据库健康探针
modules/access/contracts/         用户、项目、环境的合同
modules/access/core/              登录与项目同步流程
modules/access/adapter/           禅道、加密与PostgreSQL适配
modules/access/adapter/migrations/ access模块迁移（access schema，独立账本）
```

仍可用的能力：

- 禅道登录、内部会话、项目同步和项目权限检查。
- 环境查询、创建和重命名。
- 健康检查、结构化日志、进程关闭处理。
- 下载资源相关HTTP接口。
- MCP传输基础；默认拒绝未经验证的Token，没有注册业务工具。
- 管理CLI的配置检查与迁移命令。

已经删除的业务实现：采集接收、接口结构整理、证据提取、目录重构、知识候选、发布与回退。worker当前空闲，不消费这些旧业务任务。

仓库曾讨论过intake、knowledge、rebuild等名称和拆分方式，那是此前agent的职责草案，**不是要求接手者照抄的架构**。可以提出不同的模块划分和数据流，只需满足用户对清楚边界、可验证隔离、合同对齐及逐步开发的要求。
